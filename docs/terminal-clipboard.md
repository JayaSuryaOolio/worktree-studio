# Terminal copy/paste: how it works and why

Kept separate from `docs/architecture.md` on purpose — this is deep, low-level xterm.js/tmux mechanism detail that's rarely needed (the 80% you skip), not the core architecture every session needs to re-read (the 20% that matters). Read this only when copy/paste in a terminal panel is broken or behaving unexpectedly.

## Problem 1: Ctrl+C/Ctrl+V did nothing at all

**Symptom** (as reported): in a plain shell inside a terminal panel, selecting text and pressing Ctrl+C copied nothing; Ctrl+V pasted nothing.

**Root cause**: xterm.js's own key handling calls `preventDefault()` on virtually every keystroke it translates into pty bytes — including Ctrl+C, which needs to reach the shell as a real `0x03`/SIGINT byte for a terminal to work at all. That same `preventDefault()` also blocks the browser's native copy action from ever firing. This is a known, common gap in xterm.js integrations, not a regression — the embedding app is expected to wire this up itself.

**Fix** (`Terminal.tsx`, `term.attachCustomKeyEventHandler`):
- Ctrl+C/Cmd+C: if there's an active `term.getSelection()`, copy it via `navigator.clipboard.writeText` and suppress the keystroke (`return false`) so it doesn't *also* send a literal SIGINT. With no selection, let it through as a normal interrupt — this is what keeps Ctrl+C at a running prompt working exactly as before.
- Ctrl+V/Cmd+V: read the clipboard explicitly (`navigator.clipboard.readText()` → `term.paste(text)`) rather than relying on xterm's own native-`paste`-event wiring (which does exist — a listener on its hidden textarea — but firing *in addition to* explicit handling would double-paste; see the bug below).
- The key-combo decision logic (`classifyTerminalKeyEvent`, exported from `Terminal.tsx`) is a small pure function extracted specifically so it's unit-testable without a real browser (`Terminal.test.tsx`) — the clipboard/xterm glue itself isn't testable in this environment (no browser automation tool connected).

**A bug found immediately after, while explaining the design** (not caught by the test suite — pure key-combo classification tests can't see this): the paste branch returned `false` from `attachCustomKeyEventHandler` but never called `event.preventDefault()`. Returning `false` only skips xterm.js's *own* keydown→bytes translation — it does not suppress the browser's native default action. Since xterm.js already has its own listener for the native `paste` ClipboardEvent (a separate code path entirely, not gated by `attachCustomKeyEventHandler`), leaving the keydown un-prevented meant that listener could still fire alongside the explicit `clipboard.readText()`/`term.paste()` call, pasting the clipboard twice. Fixed by adding `event.preventDefault()` to the paste branch. (The copy branch doesn't need it — a redundant native copy of the exact same selection text is harmless.)

## Problem 2: copy still didn't work *inside* a `claude` session (though it worked in a plain shell)

**Symptom**: the fix above worked for a plain shell, but selecting text inside a running `claude` session and pressing Ctrl+C still copied nothing.

**Root cause, confirmed empirically, not guessed**:
1. `strings` on the `claude` binary shows `[?1000h`/`[?1006h` (mouse-tracking-enable escape sequences) and `mouseTrack` identifiers — `claude`'s TUI turns on mouse reporting, presumably for its own scroll/click UI.
2. Reading `@xterm/xterm`'s own source directly confirms the consequence:
   ```js
   this.coreMouseService.areMouseEventsActive
     ? this._selectionService.disable()
     : this._selectionService.enable();
   ```
   When an app has mouse tracking active, xterm.js **completely disables its own text-selection mechanism** — there's no modifier-key override in this version (`@xterm/xterm` v6). So there was never a selection for Ctrl+C to act on in the first place; this is a different, deeper issue than Problem 1, not a regression of the Problem 1 fix.

This isn't specific to `claude` — any TUI that enables mouse tracking (`vim`, `less -R`, `fzf`, `tmux` itself) has the exact same effect. Every terminal emulator, native or web, has to solve this the same way (there's no way to know "the user wants to copy their mouse selection" vs. "the running program wants this exact mouse event" except by checking, at the moment of interaction, whether a selection exists — information that only exists in the terminal-emulator layer, never in the byte stream the shell/tmux/claude ever see).

**Considered and rejected**: stripping the mouse-tracking-enable escape sequences before they reach xterm.js, so it never learns an app asked for mouse mode. Rejected because it would silently take away any real mouse-driven UI feature `claude`'s TUI has (not verified how much it has, if any) — trading "can't copy" for "can't click things in claude," not actually removing the tradeoff.

**First fix shipped: tmux copy-mode (keyboard) + OSC 52 clipboard passthrough.** `internal/term.Manager.CreateSession` runs `tmux set-option -g set-clipboard on` after creating each session (a tmux **server** option — affects every session on the machine, deliberately). `Terminal.tsx` loads the official `@xterm/addon-clipboard`, which registers an OSC 52 handler and writes decoded clipboard-set sequences to the real browser clipboard (requires `allowProposedApi: true` — its `registerOscHandler` use is gated behind that flag in this xterm.js version). To copy: enter tmux's copy-mode (`Ctrl+b` then `[`), move/select, `Enter` to copy. **This worked exactly as designed** (verified by attaching a real pty to a throwaway tmux session and driving `copy-mode`/`select-line`/`copy-selection-and-cancel`, capturing a genuine `\x1b]52;;<base64>\x07` sequence) — but the user reported it still didn't feel like "it worked" because they were still trying to drag-select with the mouse, which — per the root cause above — is unavoidably impossible with only this fix in place.

**Superseding fix: also turn on tmux's *own* mouse handling (`set -g mouse on`), not just `set-clipboard`.** These are two separate tmux options — the first fix only added `set-clipboard`. With `mouse on`, **tmux itself** requests mouse tracking from the outer terminal and intercepts every mouse event *before* it ever reaches the program in the pane — so a plain mouse-drag is captured by tmux's own drag-select, and release-to-copy triggers the same OSC 52 relay automatically, no keyboard step needed, regardless of whether `claude` (or anything else in the pane) has its own mouse tracking on. This restores the original "just drag and it's copied" workflow, uniformly, inside `claude` or a plain shell.

- **Real, empirical verification, not just reasoning**: simulated an actual mouse press→drag→release using raw SGR mouse escape codes (`\x1b[<0;x;yM` / `\x1b[<32;x;yM` / `\x1b[<0;x;ym` — exactly the byte shape a browser sends) fed directly into a throwaway tmux session's pty with `mouse on` + `set-clipboard on`, and confirmed a genuine `\x1b]52;;<base64>\x07` sequence containing the dragged text came out on release. Confirmed against a live isolated server that `CreateSession` flips both `mouse` and `set-clipboard` from `off` to `on`.
- **The one real tradeoff**: `mouse on` is also a tmux **server** option (same global-scope caveat as `set-clipboard`), and it means tmux — not the browser terminal — now owns mouse handling for every session, including plain shells. The concrete effect: mouse-wheel scrolling in a plain shell now enters tmux's own scrollback/copy-mode view instead of scrolling the browser's native xterm.js view directly. This is standard, expected tmux behavior once `mouse on` is set (not a bug), just different from before. Given `claude` is the dominant use case, this was accepted as worth it.
- The keyboard copy-mode workflow from the first fix still works too (tmux's own copy-mode command is unaffected by the mouse setting) — it's just no longer the *only* way.

## Problem 3: mouse-drag copy set tmux's own buffer but never reached the browser clipboard

**Symptom**: dragging to select text (the exact workflow Problem 2's fix was supposed to enable) copied nothing into the actual browser clipboard — `tmux show-buffer` proved tmux itself had captured the dragged text into its internal paste buffer, but nothing ended up in `navigator.clipboard`.

**Root cause, confirmed empirically by inspecting the actual websocket frames**: `mouse on` and `set-clipboard on` (Problem 2's fix) are necessary but not sufficient. tmux's own **default key bindings** for both a mouse-drag release and pressing `Enter` inside copy-mode are `send-keys -X copy-pipe-and-cancel` (confirmed via `tmux list-keys -T copy-mode-vi`), not `copy-selection-and-cancel`. Both commands copy into tmux's paste buffer, but only `copy-selection` also emits the `\x1b]52;...\x07` OSC 52 escape sequence that `@xterm/addon-clipboard` is listening for; `copy-pipe` instead hands the text to an external shell command (`copy-command`, empty by default), which is a dead end as far as the browser is concerned — no OSC 52 ever gets sent, so the addon has nothing to write to `navigator.clipboard.writeText`.

Caught a false positive during earlier manual verification of Problem 2: driving `copy-mode`/`select-line`/**`copy-selection-and-cancel`** by hand and observing a real OSC 52 sequence come out was correct as far as it went, but it exercised a command the actual default key bindings never call — a real mouse drag or a real Enter-in-copy-mode both hit `copy-pipe-and-cancel` instead, which silently does not relay to the browser. Confirmed with a byte-level A/B: forcing `copy-selection-and-cancel` via `tmux send-keys -X` produces a captured `\x1b]52;` frame on the websocket; forcing `copy-pipe-and-cancel` (the real default) on the identical selection produces no OSC 52 frame at all.

**Fix** (`internal/term.Manager.CreateSession`): rebind `MouseDragEnd1Pane` and `Enter` in both the `copy-mode` and `copy-mode-vi` key tables (mode-keys can be either, so both are covered) to `send-keys -X copy-selection-and-cancel`, right after the `set-clipboard`/`mouse` options. Like those two options, tmux key tables are server-global — no per-session scope exists, so this is a one-time server-wide rebind, not something each session needs to repeat. Verified after the fix: the identical mouse-drag-release that previously produced zero OSC 52 frames now produces `\x1b]52;;<base64>\x07` containing exactly the dragged text.

## "Should we use a tmux plugin for this instead?"

Asked directly, considered, and the answer is no: **both options above (`set-clipboard`, `mouse`) are built into tmux itself** — no plugin, no new dependency, no third-party code to vet, pin, or worry about supply-chain risk for. A well-known plugin like `tmux-yank` exists and is popular for exactly this kind of clipboard integration, but it's largely a convenience wrapper around the same underlying mechanism (OSC 52 + mouse/copy-mode) that these two native `set-option` calls already achieve directly. Since the goal was already fully reachable with zero added surface, reaching for an external plugin here would have been strictly worse from a security standpoint for no functional gain.

## Interaction with link-clicking, genuinely unverified

`Terminal.tsx` also has a `linkHandler` (see its own comment) so clicking an OSC 8 hyperlink — which `claude` really does emit, confirmed via `strings` on its binary — skips xterm.js's default scary `confirm()` dialog and opens directly. Whether the click even reaches that handler at all is a separate, **not resolved** question: xterm.js's link-click activation is a *browser-side* feature (its `Linkifier`/`OscLinkProvider`), and if it's gated by the same `coreMouseService.areMouseEventsActive` check that disables text selection (unconfirmed either way from reading the source — `Linkifier` appeared to be wired up independently of that specific toggle, but that's not the same as proving it isn't affected), then turning on `mouse on` — which makes tmux request mouse tracking from the outer terminal *unconditionally*, for every session — could mean link clicks stop reaching xterm.js's own handler **everywhere**, not just inside `claude`, including a plain shell that happens to print a hyperlink. This wasn't true before the `mouse on` change (a plain shell never requested mouse tracking on its own). Genuinely don't know without live testing — report back whether link-clicking behaves differently in a plain shell now too, not just inside `claude`.

## A related, NOT-yet-tried option worth knowing about

While reading xterm.js's default options, found `macOptionClickForcesSelection: false` — a real xterm.js constructor option, currently unset/default here. Its docs describe forcing selection when the Option key is held on macOS. Superseded in practical relevance by the `mouse on` fix above (which solves the same problem more completely, working for a plain click-drag with no modifier key at all) — left here for the record, still not implemented or verified.

## If copy/paste still doesn't work after all this

1. Confirm `tmux show-options -g mouse` and `tmux show-options -g set-clipboard` both report `on` on the machine running the server — if a terminal was created before this feature existed, both options only get set the *next* time `CreateSession` runs, not retroactively (though since they're server-wide, creating even one *new* terminal anywhere turns them on for every existing session too).
2. Confirm the browser actually granted clipboard permission — `navigator.clipboard.writeText`/`readText` can silently fail if permission was denied; check the browser's own site-permission UI for `localhost:8787` (or whatever port).
3. Confirm you rebuilt the frontend (`bun run build`) and restarted the actual server process you're testing against — these are code changes, not config a running old binary would pick up.
4. If dragging still doesn't work but the tmux copy-mode keyboard shortcut does: that specifically would point at the mouse-event-simulation path (browser → xterm.js → pty) rather than the OSC 52 relay itself, since the keyboard path bypasses mouse handling entirely — worth mentioning which one you tried if reporting this further.

# Terminal copy/paste: how it works and why

Kept separate from `docs/architecture.md` on purpose — this is deep, low-level xterm.js/tmux mechanism detail that's rarely needed (the 80% you skip), not the core architecture every session needs to re-read (the 20% that matters). Read this only when copy/paste in a terminal panel is broken or behaving unexpectedly.

## Problem 1: Ctrl+C/Ctrl+V did nothing at all

**Symptom** (as reported): in a plain shell inside a terminal panel, selecting text and pressing Ctrl+C copied nothing; Ctrl+V pasted nothing.

**Root cause**: xterm.js's own key handling calls `preventDefault()` on virtually every keystroke it translates into pty bytes — including Ctrl+C, which needs to reach the shell as a real `0x03`/SIGINT byte for a terminal to work at all. That same `preventDefault()` also blocks the browser's native copy action from ever firing. This is a known, common gap in xterm.js integrations, not a regression — the embedding app is expected to wire this up itself.

**Fix** (`Terminal.tsx`, `term.attachCustomKeyEventHandler`):
- Ctrl+C/Cmd+C: if there's an active `term.getSelection()`, copy it via `navigator.clipboard.writeText` and suppress the keystroke (`return false`) so it doesn't *also* send a literal SIGINT. With no selection, let it through as a normal interrupt — this is what keeps Ctrl+C at a running prompt working exactly as before.
- Ctrl+V/Cmd+V: read the clipboard explicitly (`navigator.clipboard.readText()` → `term.paste(text)`) rather than relying on xterm's own native-`paste`-event wiring (which does exist — a listener on its hidden textarea — but firing *in addition to* explicit handling would double-paste; see the bug below).
- The key-combo decision logic (`classifyTerminalKeyEvent`, exported from `Terminal.tsx`) is a small pure function extracted specifically so it's unit-testable without a real browser (`Terminal.test.tsx`) — the clipboard/xterm glue itself isn't testable in this environment (no browser automation tool connected).

**A bug found immediately after, while explaining the design** (not caught by the test suite — pure key-combo classification tests can't see this): the paste branch returned `false` from `attachCustomKeyEventHandler` but never called `event.preventDefault()`. Returning `false` only skips xterm.js's *own* keydown→bytes translation — it does not suppress the browser's native default action. Since xterm.js already has its own listener for the native `paste` ClipboardEvent (a separate code path entirely, not gated by `attachCustomKeyEventHandler`), leaving the keydown un-prevented meant that listener could still fire alongside the explicit `clipboard.readText()`/`term.paste()` call, pasting the clipboard twice. Fixed by adding `event.preventDefault()` to the paste branch. (The copy branch doesn't need it — a redundant native copy of the exact same selection text is harmless.)

## Problem 2: copy still didn't work *inside* a `claude` session (though it worked in a plain shell)

**Symptom**: the fix above worked for a plain shell, but selecting text inside a running `claude` session and pressing Ctrl+C still copied nothing.

**Root cause, confirmed empirically, not guessed**:
1. `strings` on the `claude` binary shows `[?1000h`/`[?1006h` (mouse-tracking-enable escape sequences) and `mouseTrack` identifiers — `claude`'s TUI turns on mouse reporting, presumably for its own scroll/click UI.
2. Reading `@xterm/xterm`'s own source directly confirms the consequence:
   ```js
   this.coreMouseService.areMouseEventsActive
     ? this._selectionService.disable()
     : this._selectionService.enable();
   ```
   When an app has mouse tracking active, xterm.js **completely disables its own text-selection mechanism** — there's no modifier-key override in this version (`@xterm/xterm` v6). So there was never a selection for Ctrl+C to act on in the first place; this is a different, deeper issue than Problem 1, not a regression of the Problem 1 fix.

This isn't specific to `claude` — any TUI that enables mouse tracking (`vim`, `less -R`, `fzf`, `tmux` itself) has the exact same effect. Every terminal emulator, native or web, has to solve this the same way (there's no way to know "the user wants to copy their mouse selection" vs. "the running program wants this exact mouse event" except by checking, at the moment of interaction, whether a selection exists — information that only exists in the terminal-emulator layer, never in the byte stream the shell/tmux/claude ever see).

**Considered and rejected**: stripping the mouse-tracking-enable escape sequences before they reach xterm.js, so it never learns an app asked for mouse mode. Rejected because it would silently take away any real mouse-driven UI feature `claude`'s TUI has (not verified how much it has, if any) — trading "can't copy" for "can't click things in claude," not actually removing the tradeoff.

**First fix shipped: tmux copy-mode (keyboard) + OSC 52 clipboard passthrough.** `internal/term.Manager.CreateSession` runs `tmux set-option -g set-clipboard on` after creating each session (a tmux **server** option — affects every session on the machine, deliberately). `Terminal.tsx` loads the official `@xterm/addon-clipboard`, which registers an OSC 52 handler and writes decoded clipboard-set sequences to the real browser clipboard (requires `allowProposedApi: true` — its `registerOscHandler` use is gated behind that flag in this xterm.js version). To copy: enter tmux's copy-mode (`Ctrl+b` then `[`), move/select, `Enter` to copy. **This worked exactly as designed** (verified by attaching a real pty to a throwaway tmux session and driving `copy-mode`/`select-line`/`copy-selection-and-cancel`, capturing a genuine `\x1b]52;;<base64>\x07` sequence) — but the user reported it still didn't feel like "it worked" because they were still trying to drag-select with the mouse, which — per the root cause above — is unavoidably impossible with only this fix in place.

**Superseding fix: also turn on tmux's *own* mouse handling (`set -g mouse on`), not just `set-clipboard`.** These are two separate tmux options — the first fix only added `set-clipboard`. With `mouse on`, **tmux itself** requests mouse tracking from the outer terminal and intercepts every mouse event *before* it ever reaches the program in the pane — so a plain mouse-drag is captured by tmux's own drag-select, and release-to-copy triggers the same OSC 52 relay automatically, no keyboard step needed, regardless of whether `claude` (or anything else in the pane) has its own mouse tracking on. This restores the original "just drag and it's copied" workflow, uniformly, inside `claude` or a plain shell.

- **Real, empirical verification, not just reasoning**: simulated an actual mouse press→drag→release using raw SGR mouse escape codes (`\x1b[<0;x;yM` / `\x1b[<32;x;yM` / `\x1b[<0;x;ym` — exactly the byte shape a browser sends) fed directly into a throwaway tmux session's pty with `mouse on` + `set-clipboard on`, and confirmed a genuine `\x1b]52;;<base64>\x07` sequence containing the dragged text came out on release. Confirmed against a live isolated server that `CreateSession` flips both `mouse` and `set-clipboard` from `off` to `on`.
- **The one real tradeoff**: `mouse on` is also a tmux **server** option (same global-scope caveat as `set-clipboard`), and it means tmux — not the browser terminal — now owns mouse handling for every session, including plain shells. The concrete effect: mouse-wheel scrolling in a plain shell now enters tmux's own scrollback/copy-mode view instead of scrolling the browser's native xterm.js view directly. This is standard, expected tmux behavior once `mouse on` is set (not a bug), just different from before. Given `claude` is the dominant use case, this was accepted as worth it.
- The keyboard copy-mode workflow from the first fix still works too (tmux's own copy-mode command is unaffected by the mouse setting) — it's just no longer the *only* way.

## Problem 3: mouse-drag copy set tmux's own buffer but never reached the browser clipboard

**Symptom**: dragging to select text (the exact workflow Problem 2's fix was supposed to enable) copied nothing into the actual browser clipboard — `tmux show-buffer` proved tmux itself had captured the dragged text into its internal paste buffer, but nothing ended up in `navigator.clipboard`.

**Root cause, confirmed empirically by inspecting the actual websocket frames**: `mouse on` and `set-clipboard on` (Problem 2's fix) are necessary but not sufficient. tmux's own **default key bindings** for both a mouse-drag release and pressing `Enter` inside copy-mode are `send-keys -X copy-pipe-and-cancel` (confirmed via `tmux list-keys -T copy-mode-vi`), not `copy-selection-and-cancel`. Both commands copy into tmux's paste buffer, but only `copy-selection` also emits the `\x1b]52;...\x07` OSC 52 escape sequence that `@xterm/addon-clipboard` is listening for; `copy-pipe` instead hands the text to an external shell command (`copy-command`, empty by default), which is a dead end as far as the browser is concerned — no OSC 52 ever gets sent, so the addon has nothing to write to `navigator.clipboard.writeText`.

Caught a false positive during earlier manual verification of Problem 2: driving `copy-mode`/`select-line`/**`copy-selection-and-cancel`** by hand and observing a real OSC 52 sequence come out was correct as far as it went, but it exercised a command the actual default key bindings never call — a real mouse drag or a real Enter-in-copy-mode both hit `copy-pipe-and-cancel` instead, which silently does not relay to the browser. Confirmed with a byte-level A/B: forcing `copy-selection-and-cancel` via `tmux send-keys -X` produces a captured `\x1b]52;` frame on the websocket; forcing `copy-pipe-and-cancel` (the real default) on the identical selection produces no OSC 52 frame at all.

**Fix** (`internal/term.Manager.CreateSession`): rebind `MouseDragEnd1Pane` and `Enter` in both the `copy-mode` and `copy-mode-vi` key tables (mode-keys can be either, so both are covered) to `send-keys -X copy-selection-and-cancel`, right after the `set-clipboard`/`mouse` options. Like those two options, tmux key tables are server-global — no per-session scope exists, so this is a one-time server-wide rebind, not something each session needs to repeat. Verified after the fix: the identical mouse-drag-release that previously produced zero OSC 52 frames now produces `\x1b]52;;<base64>\x07` containing exactly the dragged text.

## "Should we use a tmux plugin for this instead?"

Asked directly, considered, and the answer is no: **both options above (`set-clipboard`, `mouse`) are built into tmux itself** — no plugin, no new dependency, no third-party code to vet, pin, or worry about supply-chain risk for. A well-known plugin like `tmux-yank` exists and is popular for exactly this kind of clipboard integration, but it's largely a convenience wrapper around the same underlying mechanism (OSC 52 + mouse/copy-mode) that these two native `set-option` calls already achieve directly. Since the goal was already fully reachable with zero added surface, reaching for an external plugin here would have been strictly worse from a security standpoint for no functional gain.

## Interaction with link-clicking, genuinely unverified

`Terminal.tsx` also has a `linkHandler` (see its own comment) so clicking an OSC 8 hyperlink — which `claude` really does emit, confirmed via `strings` on its binary — skips xterm.js's default scary `confirm()` dialog and opens directly. Whether the click even reaches that handler at all is a separate, **not resolved** question: xterm.js's link-click activation is a *browser-side* feature (its `Linkifier`/`OscLinkProvider`), and if it's gated by the same `coreMouseService.areMouseEventsActive` check that disables text selection (unconfirmed either way from reading the source — `Linkifier` appeared to be wired up independently of that specific toggle, but that's not the same as proving it isn't affected), then turning on `mouse on` — which makes tmux request mouse tracking from the outer terminal *unconditionally*, for every session — could mean link clicks stop reaching xterm.js's own handler **everywhere**, not just inside `claude`, including a plain shell that happens to print a hyperlink. This wasn't true before the `mouse on` change (a plain shell never requested mouse tracking on its own). Genuinely don't know without live testing — report back whether link-clicking behaves differently in a plain shell now too, not just inside `claude`.

## A related, NOT-yet-tried option worth knowing about

While reading xterm.js's default options, found `macOptionClickForcesSelection: false` — a real xterm.js constructor option, currently unset/default here. Its docs describe forcing selection when the Option key is held on macOS. Superseded in practical relevance by the `mouse on` fix above (which solves the same problem more completely, working for a plain click-drag with no modifier key at all) — left here for the record, still not implemented or verified.

## Problem 4: `mouse on` was itself a regression — broken links, unreliable copy even with Shift

**Symptom, reported directly after Problems 2/3 shipped** (not a hypothetical — this is the actual real-world experience, not the byte-level tmux simulation every fix above was "verified" against):
1. A plain mouse drag in a tmux shell (no `claude`/vim running) visually selects, then the highlight disappears the instant the mouse button is released.
2. Holding Shift or Option during the drag makes the highlight persist after mouseup — but Cmd+C copies nothing, and the browser's own right-click "Copy" menu item is greyed out (doesn't think there's a selection at all).
3. Inside a `claude` session, selecting and copying only ever grabs a single word, never the full dragged range.
4. No OSC 8 hyperlink (from `claude` or a plain shell) is clickable anymore, anywhere.

**Root cause — confirmed by reading xterm.js's own source (`@xterm/xterm` v6, `src/browser/services/SelectionService.ts` and `src/browser/renderer/dom/DomRenderer.ts`), not reasoning from the outside:**

- `mouse on` (Problem 2's fix) makes **tmux** request mouse tracking from the OUTER terminal — i.e. from xterm.js itself — unconditionally, for every session on the machine. xterm.js has no way to distinguish "tmux wants this for its own copy-mode" from "`claude` wants this for its own UI": both arrive as the identical DECSET escape sequence, so xterm.js's `coreMouseService.areMouseEventsActive` is now permanently true for every pane, not just ones running a mouse-hungry program. This explains symptom 4 directly: this same "is mouse tracking active" state is what the `SelectionService` checks — turning it on globally was expected to only affect copy-by-drag, but it's a broader signal than that.
  - (Ruled out empirically, though: xterm.js's `Linkifier` — the class that actually activates OSC 8 link clicks — does **not** check `coreMouseService`/`_enabled` anywhere in its own source. So symptom 4 is real, but its exact mechanism is still open; see the note below.)
- Symptom 1 is tmux's own copy-mode behaving exactly as designed, just confusingly: `MouseDragEnd1Pane` is bound to `copy-selection-and-cancel` (Problem 3's fix) — the "-and-cancel" exits copy-mode immediately on release, which visually clears the highlight, even though the OSC 52 copy itself did succeed. No visual confirmation that anything happened is a real UX problem, just not a copy failure.
- Symptoms 2 and 3 are the deeper bug. `SelectionService.handleMouseDown` (confirmed by reading it directly):
  ```ts
  // Allow selection when using a specific modifier key, even when disabled
  if (!this._enabled) {
    if (!this.shouldForceSelection(event)) { return; }
    event.stopPropagation(); // don't send the mouse down event to the current process
  }
  // Tell the browser not to start a regular selection
  event.preventDefault();
  ```
  `shouldForceSelection` does return true for a plain Shift-held click (on Linux/Windows; Option on macOS with `macOptionClickForcesSelection`) — xterm.js **does** have a modifier override, contrary to what Problem 2 originally concluded. But `event.preventDefault()` runs unconditionally right after, regardless of whether force-selection engaged — so the browser's own native selection is blocked either way, and what the Shift-forced path actually produces is xterm's own **synthetic** selection (`SELECTION_CLASS = 'xterm-selection'`, a plain rendered `<div>` — see `DomRenderer.ts`), never a real `document.getSelection()` Range. That's exactly symptom 2's second half (the greyed-out native browser Copy menu item — there genuinely is no real `document.getSelection()` for it to act on). Why `Cmd+C`/`term.getSelection()` *also* failed to copy the same (real, xterm-internal) selection is the actual remaining open question — see below, since the mechanism producing that selection reads as correct from source. Symptom 3 (word-only copy inside `claude`) is consistent with `claude`'s own inner mouse tracking winning arbitration over tmux's, so tmux's copy-mode drag-select never engages there at all — what's actually being copied is xterm's ordinary double-click word-select, a different, much narrower action than a real drag.

**A tempting but WRONG fix, tried and reverted: bypass xterm.js's mouse handling entirely on Shift and let the browser's own native `document.getSelection()` take over.** This was implemented, then reverted before shipping, once `xtermjs/xterm.js#670` ("Reimplement selection in the terminal") was found: xterm.js used to rely on native browser selection and deliberately moved away from it years ago, specifically because native selection can only ever cover text currently rendered in the DOM viewport, and xterm.js only keeps a small rendered window of a scrollback buffer that can be thousands of lines — real native selection is physically unable to "drag past the bottom edge and keep scrolling to extend the selection into content not yet rendered," which xterm's own buffer-based `SelectionService` handles correctly by design. Bypassing it to get native selection back would have silently reintroduced exactly that bug for any selection needing to scroll mid-drag — trading one real bug for a different, more fundamental one, for a component whose whole job is getting this right. Not shipped.

**The actual, proper fix: stop tmux from making the problem worse, and use xterm.js's own already-correct force-selection mechanism as-is — don't build a replacement for it.**

`SelectionService.handleMouseDown`'s force-selection path (`shouldForceSelection` returning true for Shift on Linux/Windows, Option on macOS) does **not** take a degraded shortcut — reading further into `_handleSingleClick`/`_handleMouseMove`, it runs through the exact same buffer-coordinate-based selection model as ordinary selection, with no additional `_enabled` gating anywhere in the mousemove/mouseup continuation. Scrollback, wide characters, multi-line drags — all of it should work identically whether the selection was force-triggered or not, because it's the same code. This is the correct, already-proper mechanism; there is no need to reimplement it.

So the real fix here is narrower than it first looked:

1. `internal/term.CreateSession` no longer sets `mouse on`; `set-clipboard on` and the copy-mode keybind rebind (Problem 3) stay, so keyboard-driven tmux copy-mode (`Ctrl+b [`, select, `Enter`) still relays to the clipboard via OSC 52. `term.DisableGlobalMouseAndPassthroughCapture` reverts the option back to `off` once at server startup, so an installation that already hit this regression doesn't need to open a fresh terminal to get corrected (mouse is server-wide, so any existing session benefits immediately once it's off, not just new ones).

**Verified working, live, by direct user report after this landed**: plain-shell drag-select and copy work correctly again. Symptom 3 (word-only copy inside `claude`) turned out to be a red herring from an earlier, mistaken framing of the problem — see Problem 5.

**This revert was itself reverted the next day — see Problem 6.** Turning `mouse off` fixed the selection/copy regression described here, but it turned out to be the direct cause of a different, equally serious regression (wheel-scroll turning into shell-history navigation, in every plain shell) that hadn't been tested yet at the time this section was written. `mouse on` is back; the force-selection mechanism described above is still the correct way to get native selection while it's on.

**Prior art check, since this is worth knowing**: this was never a "no proper solution exists" situation. xterm.js's own force-selection mechanism (`shouldForceSelection`) reuses the exact same buffer-aware model as ordinary selection, and this whole stack — xterm.js underlying VS Code (desktop and web), code-server, GitHub Codespaces, ttyd, GoTTY, Wetty — is mature, widely deployed technology. That said, getting the whole chain right in practice is genuinely fiddly, and real products still have open bugs in this exact space: code-server has a filed, unresolved report of this identical "fullscreen TUI mode breaks copy" symptom, and Claude Code itself has two open upstream issues on this same mouse-capture-vs-selection tension.

## Problem 5: `claude`'s own OSC 52 write was being silently dropped by tmux — the diagnosis was right, the fix was too broad, reverted

**Symptom, after Problem 4's fix landed**: plain-shell copy confirmed working. Still broken inside `claude`: dragging shows a highlight (with or without Shift — not gated by a modifier at all, unlike the plain-shell case), but nothing ends up in the clipboard. Direct user observation that cracked this open: *"it seems different — maybe claude is capturing."*

**Root cause — a completely different mechanism than Problems 2-4:** `claude`'s TUI has its own built-in "copy-on-select" feature (per its own changelog — this isn't xterm.js's `SelectionService` or tmux's copy-mode at all, which is exactly why the highlight didn't care about Shift the way the plain-shell case does). On mouseup, `claude` emits its own OSC 52 clipboard-set sequence directly, wrapped in a **DCS tmux-passthrough envelope** (`\x1bPtmux;...\x1b\\`) — a correct, deliberate choice on `claude`'s part for tmux compatibility, not a bug in it. tmux (3.3+) only forwards a DCS passthrough envelope when the `allow-passthrough` server option is on — its default is **off**, and with it off tmux **silently drops** the whole envelope. `set-clipboard on` (already set, Problem 2) doesn't cover this: that option governs tmux's *own* OSC 52 emission (its copy-mode), a different code path from relaying a passthrough-wrapped OSC 52 that arrived *from inside a pane*. This diagnosis held up — it's the real reason `claude`'s clipboard write never reached the browser.

**The fix tried — `tmux set-option -g allow-passthrough on` — was reverted before being confirmed as fully working, once a *different*, more serious regression showed up: it broke ordinary mouse-wheel scrolling in a completely unrelated plain shell (one that never ran `claude` at all), turning it into shell-history navigation instead.** Root cause of *that*: `allow-passthrough` is **all-or-nothing** in tmux — there's no way to scope it to just `claude`'s DCS envelopes. Enabling it for `claude`'s clipboard sake also lets through DCS-wrapped sequences from *anything else* using the same tmux-compatibility mechanism — almost certainly a shell prompt/plugin with its own mouse-reporting feature that had been silently, invisibly blocked by tmux the whole time. Once that mouse-tracking DECSET got through, it hit the exact mechanism described in Problem 4: xterm.js's `Viewport` stops handling wheel events locally whenever the negotiated mouse protocol supports wheel reporting (`browser/Viewport.ts`: `handleMouseWheel: !(type & CoreMouseEventType.WHEEL)`), and started forwarding wheel deltas to the shell instead of scrolling — which that particular shell setup evidently maps to history navigation.

**Verdict: not shipped.** `internal/term.CreateSession` no longer sets `allow-passthrough`; `DisableGlobalMouseAndPassthroughCapture` (renamed from the Problem 4 version) reverts it back to `off` at startup too, for an installation that already ran this regressed version. `claude`'s own OSC 52 copy-on-select remains a known, deliberately unfixed gap — breaking basic scrolling for every shell on the machine is a materially worse outcome than that gap, and there's no tmux-level way to fix it more narrowly. If this gets revisited, it needs a fix scoped to the specific program/pane, not a global tmux option — not attempted here.

**Loose end, now moot for the same reason:** whether `claude`'s OSC 8 hyperlinks are wrapped the same DCS-passthrough way (plausible by analogy, never confirmed) — even if true, the same fix would carry the same unacceptable side effect, so this isn't worth chasing further via `allow-passthrough` either.

**Verification history worth remembering**: every fix up through Problem 4 was checked only by reasoning from xterm.js's source or by simulating raw bytes into a real tmux session server-side — never by an actual person, in an actual browser, doing an actual drag. Problem 5's diagnosis surfaced the same way ("it seems different — maybe claude is capturing"), and so did the reason its fix got reverted — a second real report, "scroll does not work anymore... it just toggles history of commands," caught within the same session before it could sit unnoticed. Two real regressions in one investigation, both found only by a real person doing a real thing in a real browser — reinforcing, not just restating, why nothing on this page should be trusted as "verified" without that.

## Problem 6: reverting `mouse off` (Problem 4) broke wheel-scroll everywhere — `mouse on` is necessary, not optional

**Symptom, reported the day after Problem 4/5 landed**: "Big problem, scroll does not work anymore in tmux shell - it just toggles history of commands." Confirmed it wasn't a leftover effect of the reverted Problem 5 `allow-passthrough` fix — persisted after that revert, after a hard browser reload, and in a brand-new terminal tab, in a plain shell that never ran `claude`, `vim`, or anything else with its own mouse tracking. Confirmed via direct tmux queries (`#{mouse_any_flag}`, `#{alternate_on}`, `#{pane_in_mode}`) that the affected pane's actual live state was completely ordinary — plain `zsh`, no alternate screen, no mouse mode, no copy-mode. Whatever was wrong was not server-side tmux pane state.

**Root cause, found by reading xterm.js's own wheel-handling source (`@xterm/xterm` v6, `src/browser/CoreBrowserTerminal.ts`) and confirmed with a live diagnostic (temporarily logging the raw bytes the browser sent to the pty on scroll) and a real `tmux attach-session` byte-capture probe:**

1. The diagnostic showed literal `\x1bOA`/`\x1bOB` bytes (application-cursor-keys up/down-arrow) being sent to the pty on every wheel-scroll tick, in a plain shell, with no mouse mode active anywhere. That's not a scroll — it's xterm.js manufacturing arrow-key presses.
2. xterm.js's own wheel listener explains exactly why:
   ```ts
   addDisposableListener(el, 'wheel', (ev) => {
     if (requestedEvents.wheel) return; // mouse-tracking protocol wants raw wheel reports — already handled elsewhere
     if (this._customWheelEventHandler?.(ev) === false) return false;
     if (!this.buffer.hasScrollback) {
       // no scrollback (i.e. "this looks like an alt-screen fullscreen app") →
       // convert the wheel delta into literal cursor-key bytes instead
       const sequence = C0.ESC + (applicationCursorKeys ? 'O' : '[') + (deltaY < 0 ? 'A' : 'B');
       this.coreService.triggerDataEvent(sequence, true);
       return this.cancel(ev, true);
     }
   });
   ```
   This only converts wheel-to-arrow-keys when `!this.buffer.hasScrollback` **and** `requestedEvents.wheel` is falsy (i.e. no active mouse-tracking protocol is already claiming wheel events). `mouse off` (Problem 4's revert) guarantees the second condition. The first condition — `buffer.hasScrollback` being false — turned out to be permanently true for *every* tmux-attached session, not just ones running a fullscreen program: a real `tmux attach-session` client-attach byte capture (a throwaway Python pty script driving a genuine `tmux attach-session -t <name>`) showed the very first bytes tmux sends to *any newly-attaching client* are `\x1b[?1049h\x1b[?1h...` — enter-alternate-screen plus enable-application-cursor-keys — sent unconditionally as part of tmux's own full-repaint-on-attach mechanism, regardless of whether the pane's actual current content is the normal or alternate buffer. This is completely standard, correct tmux behavior (this is how tmux always presents itself to an attaching terminal — it's tmux's own rendering surface, not a reflection of what's running inside a pane) and not something any tmux option changes.
3. Put together: **every tmux-attached xterm.js session looks, from xterm.js's point of view, exactly like a fullscreen no-scrollback program, permanently** — the "no scrollback" heuristic that xterm.js's wheel handler uses to decide "should I convert this wheel event to arrow keys" is unconditionally true for a tmux session, plain shell or not. The only thing standing between that and a broken wheel is `requestedEvents.wheel` being truthy — which requires tmux's own mouse-tracking protocol to be active, i.e. `mouse on`. With `mouse on`, the wheel event is instead sent as an SGR mouse report, which tmux's own default root-table binding (`WheelUpPane → copy-mode -e` when not already in a mouse-active mode) turns into entering copy-mode and scrolling tmux's *own* (real) scrollback — the actually-correct behavior. Without it, there is no other path: xterm.js's local buffer scrollback doesn't apply here either, since tmux's attach-time alt-screen switch means the shell's real output history was never written into whatever buffer xterm.js currently considers "active."

**This means Problem 4's revert (`mouse off`) and this bug are not two independent regressions — they're the same tradeoff from opposite sides.** `mouse on` is required for wheel-scroll to work at all in a tmux-backed xterm.js session; `mouse on` is also what disables xterm.js's *unforced* native selection (Problem 4). There is no tmux/xterm.js option that gives both simultaneously — this isn't a gap in this app's own tmux invocation, it's inherent to how tmux presents itself to any outer terminal.

**Fix**: `internal/term.CreateSession` sets `mouse on` again (alongside `set-clipboard on` and the copy-mode keybind rebind, both unaffected by this). Selection still works via the same Shift/Option force-selection mechanism documented as "the actual, proper fix" in Problem 4 — that conclusion doesn't change, it just needed `mouse on` back underneath it rather than off. `term.CorrectGlobalMouseAndPassthroughSettings` (renamed from the Problem 4/5 revert helper) now corrects an existing installation's `mouse` back to `on` (as well as `allow-passthrough` back to `off`, unchanged from Problem 5) at every startup.

**Not attempted, and deliberately so**: overriding xterm.js's wheel behavior client-side via its public `attachCustomWheelEventHandler` API (confirmed to exist and be stable in `@xterm/xterm`'s own type definitions) to bypass the "no scrollback → arrow keys" heuristic entirely, independent of the `mouse` option. Rejected because there's no way to make it actually scroll anything meaningful without tmux itself also treating the event as a mouse report — tmux, not xterm.js, owns the real scrollback for an attached session, so a client-side-only fix could at best suppress the wrong behavior, not replace it with a correct one; tmux still needs `mouse on` to interpret whatever we'd send it. Also would have meant re-implementing the exact decision xterm.js's own wheel handler already makes correctly once `mouse on` is set — the same "don't build a replacement for a mechanism that's already correct" principle from Problem 4 applies here too.

## If copy/paste still doesn't work after all this

1. Confirm `tmux show-options -g mouse` reports `on`, `tmux show-options -g allow-passthrough` reports `off`, and `tmux show-options -g set-clipboard` reports `on`, on the machine running the server (Problem 6 restored `mouse on`, reverting Problem 4's revert; Problem 5 tried and then reverted `allow-passthrough` — if either is wrong on your machine, something changed it outside this app, since `term.CorrectGlobalMouseAndPassthroughSettings` runs at every startup). All three are server-wide options, corrected retroactively via that startup call or the next `CreateSession`, applying to every existing session immediately once corrected. Otherwise, an older binary may still be running.
5. If wheel-scroll in a plain shell is cycling through command history instead of scrolling: that's `mouse` being `off` when it should be `on` — see Problem 6. Don't "fix" it by turning `mouse off` again; that trades this bug for Problem 4's selection regression.

3. Confirm you rebuilt the frontend (`bun run build`) and restarted the actual server process you're testing against — these are code changes, not config a running old binary would pick up.
4. If dragging still doesn't work but the tmux copy-mode keyboard shortcut does: that specifically would point at the mouse-event-simulation path (browser → xterm.js → pty) rather than the OSC 52 relay itself, since the keyboard path bypasses mouse handling entirely — worth mentioning which one you tried if reporting this further.

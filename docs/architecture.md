# Architecture

worktree-studio is a Go HTTP server + embedded React SPA for managing `git worktree`s across one or more registered repos. This doc is updated at the end of every build step in `PLAN.md`; it currently reflects **steps 1–5, the complete step 7 UI overhaul** (sidebar, command palette, Command Deck visual design, dockview terminal arrangement, terminal layout persistence), and several step-6-adjacent pieces built ahead of the diff/comment-to-agent part of that step: the **per-worktree audit log viewer**, worktree **lifecycle status + Archive** (now with a 60-day hard-delete retention sweep and an "Archived worktrees" UI to unarchive), **claude session tracking** (both launch-time and a real Claude Code hook), and a **global settings modal** (Installation/Appearance/Logs). Step 5 is the **CodeMirror-backed in-browser editor** (file tree, read/write, fsnotify external-change push, a VS Code escape hatch) — see "In-browser editor" below and `docs/editor.md`.

Since that initial pass, a batch of follow-up work landed (see `PROGRESS.md` for the day-by-day record, this doc only tracks the durable shape): a **light theme** alongside the original Command Deck dark one; opening a repo's own root checkout through the same worktree-detail UI as a real worktree (a synthetic `root-<repoId>` DB row); a per-worktree **source-branch picker** for new worktrees; a **sidebar hover popover** showing a worktree's full name, git status, and pull-request info (via a new `internal/gh` wrapper around the `gh` CLI); a **file-tree header** with a git-branch filter toggle and PR badge; and a **terminal cwd-mismatch check** (a faint border when a shell has drifted outside its worktree).

## Pieces that exist today

```
cmd/worktree-studio/main.go   entrypoint: chi router, embeds web/dist, graceful fallback page, reconciles tmux sessions + backfills root worktrees + sweeps expired archived worktrees at startup, mirrors its own log output to ~/.worktree-studio/server.log
web/embed.go                  go:embed all:dist (must live next to dist/, embed patterns are dir-relative)
internal/store/                SQLite registry: repos, worktrees (incl. archived_at/source_branch), terminal_sessions
internal/gitops/                shells out to `git worktree add/remove/list --porcelain`, `git status`, `git status --porcelain` (changed-file list)
internal/audit/                 JSONL audit logger, append-only
internal/term/                  tmux-backed terminal session manager: create/list/close, pty attach+resize, startup reconciliation, pane title/cwd lookup
internal/spotlight/             thin os/exec wrapper around the external `spotlight` CLI (worktree->root mirroring)
internal/gh/                    thin os/exec wrapper around the `gh` CLI — looks up a branch's pull request (or nil if it has none), same "shell out, don't reimplement" call as gitops/spotlight
internal/files/                  file tree (git ls-files)/read/write with path-traversal guards, fsnotify-backed external-change Watcher + Manager (ref-counted, shared per worktree)
internal/api/                   HTTP handlers (repos, worktrees, terminals, spotlight, files, worktree summary, server logs) + ws relays + adjective-noun name generator + slugify/id helpers
web/src/                        Vite + React + TS SPA — see "Frontend structure" below; RepoPicker/WorktreeDetail are the routed pages (a repo's own root and a real worktree share the same WorktreeDetail route via a synthetic worktree id), everything else is shared shell or a component
web/src/editors/                 layered editor-engine adapters (EditorAdapter.ts interface + registry.ts + CodeMirrorEditor.tsx) — see "In-browser editor" below
web/src/styles/                  style.css's actual rules, split by feature area (tokens.css is the color/font source of truth for both themes; style.css itself is just an @import manifest)
```

## Frontend structure (post-overhaul)

- **`Layout.tsx`** — the persistent app shell. Wraps every route via `<Outlet/>`; mounts `RepoProvider` (context), `Sidebar`, and `CommandPalette` once, above the routes, so none of them remount when navigating between pages — this app is an SPA in the literal sense, not independently-loading pages. Also owns the add-repo/new-worktree modal *state* (in its `LayoutShell` inner component), since both the sidebar's "+" buttons and the command palette need to open the same dialog instance.
- **`RepoContext.tsx`** — `RepoProvider`/`useRepoContext()`. Owns: the registered-repos list, `selectedRepoId` (derived via `useMatch("/repo/:repoId/*")`, not `useParams` — the provider is mounted *above* the matched route, so plain params wouldn't be visible there), **every** registered repo's worktrees (`worktreesByRepo: Record<repoId, Worktree[]>` — not just the selected repo's, since the sidebar nests every repo's worktrees under it, not just the current one), and a background `StatusScheduler` (`statusScheduler.ts`) polling git+spotlight status every 15s for "touched" (recently viewed) worktrees — see its own doc comment for the touch/idle policy. Also exposes `refreshSpotlightStatus(worktreeId)`, a one-off `refreshNow` call used right after a spotlight start/stop completes — without it, the sidebar's dot only caught up on the scheduler's own next naturally-due tick, up to the full 15s later, which read as the action itself being slow (a real reported bug, fixed without adding any new polling). `Sidebar.tsx` is the only consumer of the worktree-list/status half of this; `WorktreeDetail.tsx` reads `worktreesByRepo` too, for the current worktree's own path.
- **`Sidebar.tsx`** — every repo, each repo's worktrees nested directly underneath as **flight-strip rows** (see `docs/design.md`): mono branch name, a colored left-edge tab for dirty/clean (`data-dirty="true"|"false"` set explicitly per row, read by CSS — not inferred from a child element), ahead/behind tick marks when applicable, a cyan dot when spotlight is active (blinking via a `pending` class for the duration of a start/stop action). A repo's own name is itself a link — to its synthetic root worktree, not a separate "Workspace" list page (see "Root worktree" below) — highlighted green when that's what's open, the same accent an active worktree row gets. Each worktree row's `WorktreeActionsMenu` kebab holds spotlight start/stop and archive. A "+" beside "Repos" opens `AddRepoDialog`; a "+" beside each repo name opens `NewWorktreeDialog` scoped to that repo (both via the callback props from `Layout.tsx`, not owned locally). Each row is wrapped in `WorktreeHoverPopover.tsx` — see "Sidebar hover popover" below.
- **`CommandPalette.tsx`** — Cmd/Ctrl+K, built on `cmdk` (headless). Fuzzy-jumps to any repo/worktree from `RepoContext`, or triggers the same add-repo/new-worktree dialogs. Scoped deliberately narrow (jump/create only) — not arbitrary command execution.
- **`WorktreeActionsMenu.tsx`** — the shared kebab-menu component behind every per-worktree action in the sidebar. Its click handler must call **both** `preventDefault()` and `stopPropagation()` — a real bug, once shipped: when this menu is nested inside a `<Link>` (the sidebar row), `stopPropagation()` alone prevents the Link's own navigation handler from running, but does *not* suppress the anchor's native default action, so the click fell through to a full-page reload. Fixed and covered by a regression test (`WorktreeActionsMenu.test.tsx`) that dispatches a real click and checks `event.defaultPrevented`.
- **`worktreeActions.ts`** — shared delete-with-confirm-and-force-retry / spotlight-start-with-friendly-conflict-message logic, used by `Sidebar.tsx`.
- **`WorktreeDetail.tsx`** — terminal arrangement, via **dockview** (`dockview-react`), not a plain tab strip. Also renders the same UI for a repo's synthetic root worktree (see "Root worktree" below) and flags (a faint red border) a terminal pane whose shell has drifted outside its worktree (see "Terminal cwd-mismatch check" below). See "Terminal arrangement" below.
- **`Terminal.tsx`** — unchanged by the whole overhaul. Still just xterm.js + a websocket to `/ws/terminals/:id`; hosting it inside a dockview panel instead of a manually-toggled `display:none` div doesn't touch this component at all.
- **`FileTree.tsx`** / **`EditorPanel.tsx`** — the file editor's file-tree sidebar and dockview panel shell. See "In-browser editor" and "File-tree header: git filter + PR badge" below.
- **`theme.ts`** / **`filesPanelPreference.ts`** / **`rootWorktree.ts`** — small, single-purpose `localStorage`-backed preference modules (dark/light theme; file-tree-panel open/closed, global not per-worktree; the `root-<repoId>` id format), each with its own tiny test file. Same shape as `prGitCache.ts` below, just simpler (no TTL/staleness).

### Request flow

1. Browser loads `/`. `RepoProvider` (mounted in `Layout.tsx`, above every route) calls `GET /api/repos/` once, then `GET /api/repos/:id/worktrees/` for every repo returned, then a background `StatusScheduler` polls per-worktree `GET .../status` and `GET .../spotlight/` every 15s for recently-viewed worktrees. `Sidebar.tsx` renders this data as a tree; `RepoPicker.tsx` (the page under `/`) is just an empty-state message now, not a list of its own.
2. Adding a repo is a modal (`AddRepoDialog.tsx`, opened from the sidebar's "+" or the command palette) — `POST /api/repos/` with `{name, path}`. The handler validates the path is a real directory and a real git repo (`git rev-parse --is-inside-work-tree`) via `internal/gitops.IsGitRepo`, persists it via `internal/store`, appends a `repo.add` audit line, backfills its synthetic root worktree (see "Root worktree" below), and the frontend navigates straight to `/repo/:id` on success.
3. Clicking a repo's name (in the sidebar, or via the command palette) navigates straight to `/repo/:repoId/worktree/root-:repoId` — its own root checkout, through the same `WorktreeDetail.tsx` route a real worktree uses (see "Root worktree" below). `/repo/:repoId` on its own (e.g. a stale link) just redirects there — there's no separate "Workspace" list page anymore; the per-repo settings page's Worktrees tab already covers "list every worktree."
4. Creating a worktree is also a modal (`NewWorktreeDialog.tsx`, opened from the sidebar's per-repo "+" or the command palette) — immediately calls `GET /api/repos/:repoId/worktrees/new-name-suggestion` to prefill an editable adjective-noun name (e.g. `amber-ridge`) from a small embedded Go wordlist (`internal/api/wordlist.go`), and `GET /api/repos/:repoId/branches` to populate a "Create from" branch dropdown (local + remote-tracking refs, pre-selected to the repo's resolved default). Submitting calls `POST /api/repos/:repoId/worktrees/` with `{name, source_branch}`; the handler slugifies the (possibly user-edited) name, uses it as both branch name and directory name, and runs `git worktree add -b <branch> <path> <source_branch>` against the registered repo's path — creating the worktree at `~/.worktree-studio/worktrees/<repoId>/<slug>`, deliberately **outside** the source repo tree. `source_branch` (persisted on the row, shown in the repo settings page's worktree table as "Created from") beats the repo's own `base_branch` setting beats auto-detection — added because neither `base_branch` nor auto-detection ever fetches from the remote, so a new worktree is only as fresh as whenever the local branch was last pulled; picking an explicit `origin/<branch>` entry from the dropdown (or prefixing `base_branch` with `origin/` in the repo settings page) sidesteps that per-worktree or repo-wide. Persists a `worktrees` row and appends a `worktree.create` audit line. When triggered from the sidebar or palette, the frontend navigates straight into the new worktree's terminal view.
5. Archiving a worktree (its row's kebab menu, `WorktreeActionsMenu.tsx`) calls `POST .../archive` — a pure visibility flag, no git operation (see "Worktree lifecycle status" below for the full archive/unarchive/retention story). Real destructive delete (`DELETE /api/repos/:repoId/worktrees/:worktreeId`, unchanged: closes every terminal session for real via `tmux kill-session`, then `git worktree remove --force <path>` or a `409` if dirty without `--force`) still exists at the API layer and backs both the manual delete flow and the archived-worktree retention sweep.
6. Clicking a worktree (sidebar row, or the command palette) navigates to `/repo/:repoId/worktree/:worktreeId` (`WorktreeDetail.tsx`), which lists that worktree's terminal sessions via `GET .../terminals/` and renders them as dockview panels (see "Terminal arrangement" below).
7. A worktree row's Spotlight indicator/menu item calls `GET .../spotlight/` to show whether that worktree is the one currently mirrored into its repo's root, another worktree is (via `internal/spotlight.StatusForRoot`), or spotlight is unavailable (CLI not installed). "Start spotlight" calls `POST .../spotlight/start`, which shells out to the external `spotlight` CLI (`internal/spotlight.Start`, cwd = the worktree path) — a `409` means the root has uncommitted changes and the CLI itself refused, surfaced verbatim rather than retried. "Stop spotlight" calls `POST .../spotlight/stop`. Both now trigger an explicit, one-off `refreshSpotlightStatus` call right after (see the `RepoContext.tsx` bullet above) instead of waiting on the background poller. See `docs/spotlight-sync.md` for what the underlying tool actually does (worktree → root mirroring, not the reverse — a design correction recorded there).
8. Each worktree's dirty/ahead-behind status comes from `GET .../worktrees/:id/status`, which runs `internal/gitops.Status` (`git status --porcelain=2 --branch`) and returns `{branch, dirty, has_upstream, ahead, behind}`. `ahead`/`behind` are only meaningful (and only rendered) when `has_upstream` is true — a freshly created worktree's branch typically has no upstream configured at all, in which case they're correctly not shown rather than misleadingly shown as `0`.

### Root worktree

Clicking a repo's name opens its own root checkout (the main `git` working tree, not a worktree at all) through the exact same `WorktreeDetail.tsx` UI — terminals, file tree, layout persistence — a real worktree gets, per direct request ("it's useless [showing a bare list], now that settings has this already... let it be another worktree like screen").

- **`store.RootWorktreeID(repoID)`** (`"root-" + repoID`) is a synthetic `worktrees` row's id, `source = "root"` (a new enum value alongside `"created"`/`"imported"`), `path = repo.Path`. `Server.EnsureRootWorktree` inserts one (idempotently) right after a repo is registered, and `main.go` backfills it at startup for repos already registered before this existed.
- Excluded from every normal worktree listing (`handleListWorktrees`, `handleListAllWorktrees` — the latter since removed with the settings-modal Worktrees tab, see below) — it's not a real git worktree and would duplicate the repo itself in every worktree table. Reached only via `store.RootWorktreeID`, computed identically on the frontend (`rootWorktree.ts`) so the two sides can't drift.
- Because its id is a normal (if synthetic) `worktrees` row, every existing per-worktree endpoint (terminals, files, layout, status) works completely unmodified — `GetWorktree(id)` doesn't care that the row is synthetic, only the *listing* queries filter it out.
- The frontend resolves the worktree's own path (for `TerminalPanel`'s cwd-mismatch check and the file tree) as `repo.path` for a root id, `worktree.path` otherwise — `WorktreeDetail.tsx`'s `worktreePath`.

### Terminal arrangement (dockview)

- **`WorktreeDetail.tsx`** hosts a `DockviewReact` component (from `dockview-react`) instead of a manually-toggled tab strip. One dockview panel per terminal session, panel `id` == `TerminalSession.id`. The panel's component (`TerminalPanel`) is a one-line wrapper rendering the existing `<Terminal terminalId={...}/>` **unchanged** — dockview panels are just React components in the tree, so adding/splitting/resizing panels doesn't remount `Terminal.tsx` or touch its xterm/websocket lifecycle.
- **"+ New Terminal ▾" dropdown**, three actions, each first calls the existing `POST .../terminals/` to get a real `TerminalSession`, then places the panel via dockview's `addPanel({ position: { referencePanel, direction } })`:
  - **New tab** (`direction: 'within'`) — added as a tab within the currently active group; selecting it shows it full-size, sibling tabs hidden (classic tab-strip behavior, not a tile).
  - **Split right** (`direction: 'right'`) / **Split down** (`direction: 'below'`) — added as a new tile shown simultaneously alongside the reference panel. Resizable by dragging the boundary between tiles (dockview's native split-view behavior — not custom code).
- Closing a panel fires dockview's `onDidRemovePanel`, which calls the existing `DELETE .../terminals/:id` (real tmux kill) and drops it from local state.
- Each panel's `Terminal.tsx` opens its own `WebSocket` to `/ws/terminals/:id` (still one dedicated connection per terminal, not multiplexed — see `docs/session-persistence.md`'s documented simplification). Binary ws messages are raw bytes fed straight into the pty; text ws messages are JSON control frames, currently just `{"type":"resize","cols":N,"rows":N}`, sent on open and whenever xterm.js's fit addon recomputes size. The server (`handleTerminalWS`) runs `tmux attach-session -t <name>` under a pty via `creack/pty`. None of this changed by moving from a tab strip to dockview — see `docs/session-persistence.md` for the full tmux-restart-survival story.
- **Copy/paste**: Ctrl+C/Ctrl+V are handled explicitly in `Terminal.tsx` (xterm.js doesn't wire this up by default), plus a tmux-side `set-clipboard on` + `@xterm/addon-clipboard` OSC 52 relay so copying still works inside a program that's grabbed mouse tracking (e.g. `claude`'s own TUI). See **`docs/terminal-clipboard.md`** for the full mechanism, the two real bugs found along the way, and how to troubleshoot it — deliberately kept out of this file since it's deep, rarely-needed detail, not core architecture.
- Styled by overriding dockview's `--dv-*` custom properties with Command Deck's tokens (`.command-deck-dockview` in `styles/worktree-detail.css`), starting from the built-in "abyss" theme as a base — not by fighting its DOM structure. Reads `tokens.css`'s variables, so it re-themes for free on the dark/light switch. Must cover the *inactive*-tab variables too (`--dv-activegroup-hiddenpanel-tab-*`/`--dv-inactivegroup-hiddenpanel-tab-*`), not just the active/visible ones — a real bug (missing those four) left every non-selected terminal tab on the abyss theme's hardcoded near-black/white colors regardless of the selected theme, found by reading dockview's own base CSS rules rather than guessed.
- **cwd-mismatch check**: `TerminalPanel` fetches `GET .../terminals/:id/cwd` once when a panel opens (`internal/term.CurrentPath`, `tmux display-message -p "#{pane_current_path}"` — tmux's own live-tracked value, no polling of `/proc`/`lsof` needed) and compares it against the worktree's own path (prefix match, so a subdirectory doesn't count as drifted). A mismatch gets a faint red border (`.terminal-panel-inset.cwd-mismatch`). Deliberately a one-shot check, not polled — this project already has one legitimate background poller (`RepoContext.tsx`'s `StatusScheduler`, for live per-row status many rows show at once simultaneously) and a directory only changes when someone types `cd`, so a check on open is what the feature actually needs.
- **No OS-level popout into a separate browser window** — considered and explicitly ruled out for this tool, not deferred as a future TODO.
- **Layout persistence**: on mount, `GET .../layout` fetches the saved arrangement (a `404` means none saved yet, not an error); if present, `dockviewApi.fromJSON()` restores it, then `seedPanels` fills in any terminal that exists server-side but wasn't part of the saved layout (e.g. created after the last save). Every `onDidLayoutChange` (drag/resize/tab-switch) debounces a `PUT .../layout` of `dockviewApi.toJSON()` (500ms — the layout is one opaque JSON blob upserted wholesale, not worth writing on every single drag event). The server never inspects the layout's shape, just stores and returns it verbatim (`internal/api/layout.go`, `worktree_layouts` table). Verified surviving both a page reload and a full server kill+restart against a real running server.
- **Known simplification, not an oversight**: if a saved layout references a terminal id that no longer exists server-side (e.g. deleted through a path that didn't get a chance to save an updated layout first), that panel is left to fail gracefully at the websocket layer (`Terminal.tsx` shows a connection-error message) rather than this code hand-pruning dockview's serialized grid structure to remove it. A real edge case with a non-destructive fallback, not worth the complexity of generic grid-pruning logic.

### In-browser editor (CodeMirror, layered)

- **Engine layering**: `web/src/editors/EditorAdapter.ts` defines the interface (`content`, `path`, `theme`, `onChange`, `onSaveRequested`) every editing engine implements as a plain React component; `registry.ts` maps a `kind` string to an adapter (today just `{ codemirror: CodeMirrorEditor }`), mirroring the `const components = { terminal: TerminalPanel }` pattern `WorktreeDetail.tsx` already uses for dockview. `EditorPanel.tsx` (the dockview panel shell) and `FileTree.tsx` never import CodeMirror directly — only `CodeMirrorEditor.tsx` does. Swapping or adding an engine is additive there, not a rewrite. See `docs/editor-plan.md`/`docs/editor.md` for the full rationale.
- Each adapter is **uncontrolled after mount** (like `<textarea defaultValue>`, not `<input value>`) — resetting its content (e.g. after accepting an external-change reload) is done by remounting via a changed `key`, the same pattern already used to reset dockview state per worktree.
- **`internal/files`**: `ListTree` (`git ls-files` tracked ∪ `git ls-files --others --exclude-standard` untracked, nested into a tree server-side), `ReadFile`/`WriteFile` (both go through `ResolvePath`, which rejects any path escaping the worktree root — the first place this app takes an untrusted filesystem path from the browser). REST: `GET .../files/tree`, `GET/PUT .../files/content?path=...`.
- **External-change push**: `internal/files.Watcher` (fsnotify, recursive, skips `.git`) + `internal/files.Manager` (one `Watcher` shared/ref-counted per worktree across every ws subscriber) push `{"type":"changed","path":...}` over `GET /ws/files/:worktreeId`. Debounced (300ms) to collapse a burst of raw OS events into one notification per path. Own-write suppression (`MarkOwnWrite`, called **before** `WriteFile`, not after — a real race was found and fixed here, see `internal/api.TestPutFileContentSuppressesOwnWriteEvent`) stops a save from round-tripping back as a false external-change push to the tab that made it.
- `EditorPanel.tsx` opens one ws connection per open file (same one-connection-per-panel simplicity call already made for terminals, not a shared multiplexed channel). A clean buffer reloads silently on a change event for its path; a dirty one shows a reload/keep-editing banner instead of silently discarding edits or silently ignoring the change.
- **One buffer per file**: `WorktreeDetail.tsx`'s `handleOpenFile` reuses an already-open panel (`dockviewApi.getPanel("editor:" + path)`) instead of opening a second one for the same path — there's never more than one buffer on a file at once, by construction.
- **VS Code escape hatch**: `POST .../open-in-vscode` shells out to `code <worktree-path>`. Gated in the UI on `GET /api/settings/dependencies`'s `vscode_cli` entry (same `exec.LookPath` detection pattern as tmux/spotlight in `SettingsModal.tsx`), since `code` needs a one-time manual PATH-install step even when VS Code itself is present.
- Explicit save only (Cmd/Ctrl+S, bound inside `CodeMirrorEditor.tsx`'s own keymap) — no autosave.

### File-tree header: git filter + PR badge

`FileTree.tsx`'s header no longer shows the worktree/folder name (removed per direct request — no room to also fit git/PR info). In its place:
- A git-branch icon (`icons/FileTreeIcons.tsx`) toggles filtering the tree to only files changed on the current branch (`filterTreeToChangedFiles`, a pure exported function) — prunes to matching files plus every ancestor directory with at least one matching descendant, not a flat list. Disabled when there are no changed files.
- A PR badge (`#123 ↗`) appears when the branch has one, opening it in a new tab on click.
- Collapse-all got a proper two-chevron SVG icon (replacing a plain `⊟` glyph) and stays right-aligned via the heading's `justify-content: space-between`.
- Both new elements are powered by `useWorktreeSummary.ts` — see "Sidebar hover popover" below, which shares the exact same hook/cache.

### Sidebar hover popover

Sidebar rows have no room to show more than a bare ahead/behind tick, and branch names get clipped — hovering a row (900ms delay) shows `WorktreeHoverPopover.tsx`: the full worktree name, git status (ahead/behind, dirty file count, changed-file list), and the branch's pull request if any.

- **`internal/gh`** (new package) wraps `gh pr view <branch> --json number,title,state,url,isDraft` the same way `internal/spotlight` wraps its own CLI. `PRForBranch` returns `(nil, nil)` — not an error — when a branch simply has no PR (`gh`'s real stderr wording, "no pull requests found", confirmed against a live invocation, not guessed).
- **`gitops.ChangedFiles`** (new) parses `git status --porcelain` (v1, simpler to parse reliably than the richer porcelain=2 format `Status` already uses) for the changed-file list. Always returns a real (possibly empty) slice, never `nil` — a nil Go slice serializes to JSON `null`, and a consumer calling `.length` on that crashes; found as a real bug (see PROGRESS.md, 2026-08-12) after the popover's own JS threw on exactly that for the common "clean worktree" case.
- **`GET .../worktrees/:id/summary`** (`internal/api/summary.go`) combines `gitops.Status` + `ChangedFiles` + `gh.PRForBranch` into one response. Deliberately **not** cached or rate-limited server-side — that's the frontend's job, since it's the one place that knows how often someone's actually hovering.
- **`prGitCache.ts`** is the actual rate-limit mitigation: a `localStorage` cache keyed by worktree id, 5-minute TTL. `useWorktreeSummary.ts` (shared with the file-tree header above) reads it: a fresh entry is served with zero network calls; a stale/missing one is shown as-is (if cached) while a background refetch updates it. Repeat hovers within the TTL window never reach `gh`.
- **Rendered via a portal into `document.body`**, not inline where the hover target lives — an absolutely-positioned popover clipped by the sidebar's own `overflow-y: auto` no matter how it was positioned in-place; a portal is what actually escapes that. Position is computed from the row's `getBoundingClientRect()` (`computePosition`, exported for direct testing), placed to the right when there's room, flipped below otherwise.
- **Hover grace period**: entering either the row or the popover itself cancels a 150ms pending hide, so moving the mouse across the real gap between them (they're not adjacent) doesn't close it before it's reachable — a real reported bug ("closes immediately on mouse leave").

### Per-worktree audit log viewer

- `GET /api/repos/:repoId/worktrees/:worktreeId/audit-log` (`internal/api/audit.go`) reads the whole global JSONL audit log (`internal/audit.Logger.ReadAll`, new — parses every line into a `map[string]any`, skipping malformed lines rather than failing the whole read) and filters to entries whose `worktree_id` field matches, newest first. There's still only ever one physical log file — this is a read-time filter, not a per-worktree file, since the whole log is small enough for a local tool to just scan on each request. Filtered on `worktree_id` alone, not also `repo_id`: worktree ids are already globally unique (`newID()`), and not every event type logs a `repo_id` alongside `worktree_id` (e.g. `terminal.create`/`terminal.close` only log `terminal_id`+`worktree_id`) — an earlier version of this handler required both and silently dropped those two event types as a result, caught during real-server verification, not by the test suite (the Go tests all happened to use event types that do carry `repo_id`).
- Deliberately does **not** require the worktree to still exist in the store — only the repo. The point of a per-worktree log is that it outlives the worktree itself (deletion, a killed terminal session): the work's history shouldn't disappear because the live DB row did. A worktree id with no matching entries (never existed, or existed and was deleted) returns `200 []`, not a `404`.
- Frontend: `WorktreeAuditLog.tsx`, a dialog fetching this endpoint and rendering entries with a friendly icon/label per known event type (`worktree.create/remove/archive/unarchive`, `terminal.create/close`, `spotlight.start/stop`, `claude.session.create`) plus a one-line summary (branch name, tab label, claude session id) and a `<details>` raw-JSON dump for anything else — new event types (e.g. a future `diff.comment_sent` from step 6's other half) render fine automatically via the fallback, no whitelist to maintain. Opened from: the kebab menu ("View worktree log", `WorktreeActionsMenu.tsx`, in `Sidebar.tsx`) and a toolbar button inside `WorktreeDetail.tsx` for access without leaving the terminal view.
- **Event names are a typed enum, not bare strings**: `internal/audit.Event` (`internal/audit/events.go`) on the Go side, `AuditEventType` (`web/src/auditEvents.ts`) on the frontend — every call site passes a named constant (`audit.EventWorktreeCreate`, etc.), and `WorktreeAuditLog.tsx`'s `EVENT_LABELS` map is typed `Record<AuditEventType, ...>` so a Go-side event forgotten on the frontend fails to compile there, not silently renders unstyled. The two lists are hand-synced (no codegen in this project). `AuditLogEntry.event` itself stays plain `string` — the viewer must still render event types it doesn't recognize (an older frontend build against a newer backend) via the raw-JSON fallback, not refuse them. Introduced proactively per direct user request ("this module will have more complex logic coming, keep its design robust") — the planned interactive-buttons feature (`PLAN.md` TODO) is exactly the kind of logic this makes safe to build: a `switch` over `audit.Event` values to decide what button an entry gets.
- **Design principle**: the SQLite store and the audit log are complementary, not duplicates — DB = current state (a worktree's live `status`, path, terminal sessions), audit log = full history (every transition, survives deletion). Don't cache "last event" onto a `worktrees` row, and don't derive current state by scanning the log (e.g. don't compute "is this archived right now" from the last `worktree.archive`/`unarchive` line — read `worktrees.status`). Features needing both (the settings-modal datagrid, the interactive-buttons TODO — which needs current DB state to decide whether "Unarchive" should even be enabled) join across them at read time in the API layer.

### Worktree lifecycle status (active / archived / deleted) and Archive

- `worktrees.status` (migrated in for existing DBs via `Store.migrateAddWorktreeStatus`, a `PRAGMA table_info` check + conditional `ALTER TABLE` — there's no migration framework in this project, see the plain `CREATE TABLE IF NOT EXISTS` schema, so a single added column doesn't warrant one). Values: `"active"` (default), `"archived"`, `"deleted"` (constants in `internal/store`).
- `POST .../archive` / `POST .../unarchive` (`internal/api/archive.go`) just flip this column — **no git operation at all**. This is the entire point of archive vs. delete: archiving hides a worktree from the normal list (`handleListWorktrees` now defaults to `status=active` only) without destroying the git worktree, its branch, or the ability to reopen a terminal in it later — including resuming a claude session recorded against it (see below). Both transitions are audit-logged (`worktree.archive`/`worktree.unarchive`) and stamp/clear `worktrees.archived_at` (see the retention sweep below).
- The kebab menu's former "Delete" item is now "Archive" (`WorktreeActionsMenu.tsx`) — real, destructive delete (`DELETE .../worktrees/:id`, unchanged: still runs `git worktree remove` for real) is no longer reachable from the per-worktree kebab at all.
- **Browsing/unarchiving**: the per-repo settings page's Worktrees tab has an "Archived worktrees" section (`GET .../worktrees/archived`) listing each one with days-until-auto-delete and an Unarchive button (`POST .../unarchive`, same endpoint as above).
- **60-day hard-delete retention sweep** (`internal/api/archive_sweep.go`, `Server.SweepExpiredArchivedWorktrees`): removes (git worktree + DB row, via `hardRemoveWorktree` — the same teardown the manual delete endpoint uses, always forced since by 60 days archived there's no one left to ask about uncommitted changes) any worktree archived longer than `ArchivedWorktreeRetention`. Runs once at server startup (so a worktree that crossed the threshold while the server was down still gets cleaned up promptly) and every 6 hours thereafter — a real periodic job, but a deliberately coarse one; it only controls how promptly an already-expired worktree gets noticed, not a live status. `worktrees.archived_at`, stamped on archive/cleared on unarchive, is what it reads to decide "expired"; a migration backfills it (to the migration's own run time — the real archive date is unrecoverable) for rows that were already archived before this column existed, so they don't sit permanently exempt from ever being swept.
- **`"deleted"` status is unused** — the settings-modal bulk-delete datagrid it was reserved for was superseded by the retention sweep above, which hard-deletes directly rather than needing a soft-delete intermediate state.

### Claude session tracking (for future resume)

- `POST .../terminals/` accepts optional `claude_session_id`/`claude_session_title` fields. When present, `handleCreateTerminal` logs a `claude.session.create` audit event (`repo_id`, `worktree_id`, `terminal_id`, `claude_session_id`, `title`) in the same request that creates the terminal.
- The frontend (`createWorktreeWithClaudeTerminal` in `worktreeActions.ts`) generates the session id itself via `crypto.randomUUID()` **before** starting `claude`, rather than letting `claude` pick one — that's what makes it knowable to log at all. The auto-started command becomes `claude --session-id <uuid> -n <name>` (`--session-id`/`-n` are real `claude` CLI flags — verified via `claude --help`); `<name>` is the worktree's own adjective-noun name, already lowercase-alnum-and-hyphens only (`slugify`'s guarantee), so it's safe to embed directly in the command line typed into the pane's shell with no quoting.
- Why this matters independent of the terminal/tmux session's own lifecycle: the audit log entry (and thus the session id) survives the terminal being closed, the worktree being archived, or even the worktree being hard-deleted — restoring the exact same guarantee the rest of this audit-log feature already provides (see "Per-worktree audit log viewer" above). A person (or a future "Resume" button) can `cd` into the worktree path and run `claude --resume <id>` from that log entry at any later point, as long as the worktree itself hasn't actually been deleted.
- Not built yet: an actual "Resume claude session" UI action that reads the id from the log and does this automatically — today it's a manually-actionable record, not a one-click flow.

### Claude Code SessionStart hook (`internal/claudehook`)

Built to fix two real gaps in the launch-time tracking above: it only ever sees sessions worktree-studio itself starts (missing anything a person starts by hand in a plain shell), and the auto-launched terminal doesn't always actually get created (an observed race, not yet root-caused).

- **Global hook, resolved per-request**: rather than installing a hook per-worktree (impossible to do once at "install time" anyway, since worktrees are created continuously), one `SessionStart` hook is installed globally into `~/.claude/settings.json`, firing for every claude session on the machine. `POST /api/claude-hook` (`internal/api/hooks.go`) receives that hook's stdin JSON (forwarded verbatim by the installed script) and resolves its `cwd` back to a tracked worktree via `store.FindWorktreeByPath` (exact or subdirectory match, across every repo — there's no other signal to identify "which worktree"). No match is the expected common case (most sessions on a dev machine aren't in a worktree-studio worktree) and is a silent `200`, not an error.
- **The hook script**: a small generated shell script at `~/.worktree-studio/hooks/session-start.sh` (content built by `claudehook.hookScriptContent`), doing nothing but `curl -d @- <server>/api/claude-hook` with a 2s timeout, swallowing all errors, always exiting `0` — a claude session must never fail to start because worktree-studio is down.
- **Matched sessions** log the existing `claude.session.create` event with `source: "hook"` (no `title` — see the title-lookup endpoint below for that), distinguishing it from the launch-time version without needing a separate event type; both are kept, not one replacing the other.
- **Installing it is the one genuinely sensitive operation in this codebase**: `internal/claudehook/install.go` edits the user's real, global, shared-with-other-tools `~/.claude/settings.json`. Rules enforced by both the code and its tests (`install_test.go`): only ever reached via an explicit user action (the settings UI, never automatic); parses the file generically (`map[string]any`) so every key this package doesn't know about round-trips untouched; merges one new entry into `hooks.SessionStart` rather than ever replacing the array or the file; is idempotent (checked by exact script-path match, not just "does SessionStart exist"); uninstall removes only that one entry; and it backs up the file to `~/.worktree-studio/backups/claude-settings-<unix-nano>.json` before every write (see the backup/restore TODO in `PLAN.md`, which this is a narrow, already-built precedent for). Refuses to touch a settings.json that isn't valid JSON rather than guessing. Verified for real (not just unit-tested): installed against an isolated `HOME`, ran the actual generated script piping a real hook payload through it, confirmed the audit log entry appeared, uninstalled, and confirmed via `md5` that the *real* `~/.claude/settings.json` was byte-for-byte unchanged throughout.
- **Session title lookup**: `GET /api/claude-sessions/:id/title` (`claudehook.SessionTitle`) globs `~/.claude/projects/*/<id>.jsonl` (Claude Code's own transcript storage — one directory per project, named after its path with `/` replaced by `-`) and returns a clipped version of the session's first real user message, skipping meta/injected-tag content (a heuristic: skip any `user`-role message starting with `<`, since real typed prompts don't). `WorktreeAuditLog.tsx` fetches this best-effort per `claude.session.create` entry and prefers it over the stored `title` field — the only title available at all for hook-sourced entries, and a better one than the worktree name for launch-time entries too.

### Claude Code Notification hook + attention badges (`internal/attention`)

Answers "a claude session is waiting on me — which worktree, and is anyone even looking at it?" `internal/claudehook/install.go` now installs the *same* hook script under **both** `SessionStart` (above) and `Notification` — the Claude Code hook event that fires when a session is blocked on a permission prompt or has gone idle waiting for input. One script, one `/api/claude-hook` endpoint; the posted payload's own `hook_event_name` field tells `handleClaudeHook` (`internal/api/hooks.go`) which behavior to run. `IsHookInstalled`/`InstallHook`/`UninstallHook` all iterate `hookEventNames` (`["SessionStart", "Notification"]`) so the two are always installed/removed together as one "Claude session-tracking hook" dependency in the settings UI — no new UI surface needed. `InstallHook` self-heals a partial install (e.g. someone hand-edited `settings.json` and only one event's entry survived) rather than requiring an uninstall/reinstall round-trip first.

- **`internal/attention.Tracker`**: a small in-memory (never persisted — this is ephemeral "is a session currently waiting" state, not history) pending-set + pub/sub. `SetPending(worktreeID, message)`/`Clear(worktreeID)` mutate the set and fan the change out to every subscriber as an `Event`; `Snapshot()` returns the current set for a client that just connected. A slow subscriber's buffered channel filling up drops that event for it rather than blocking `SetPending`/`Clear` callers or other subscribers.
- **`claudehook.IsBlockingNotification(message)`** filters out Notification events that are just background-progress chatter (e.g. "waiting for background agents to finish") before `handleClaudeHook` ever calls `SetPending` — per direct feedback, a badge/notification firing for something that wasn't actually blocked on the user was noise, not signal. Since `message` is unstructured free text with no guaranteed wording, this is a small, extensible substring exclusion list, not a real classifier — it only knows the specific non-blocking phrasings observed so far.
- **`GET /ws/attention`** (`internal/api/attention.go`, `handleAttentionWS`) is global, not worktree-scoped (unlike `/ws/files/:id`/`/ws/terminals/:id`) — the sidebar needs to know about every worktree's pending state at once, not just whichever one is currently open. Sends `{"type":"snapshot","pending":{...}}` immediately on connect, then `{"type":"update","worktree_id":...,"pending":bool,"message":...}` per change. This had to be push-based rather than reusing the existing git-status/spotlight-status poll infrastructure (`StatusScheduler` in `RepoContext.tsx`): that scheduler only actively re-polls whichever worktree's detail page is currently open, going idle for every other worktree after one bootstrap fetch — exactly the worktrees this feature most needs to notify about.
- **`POST .../worktrees/:id/attention/clear`** dismisses a worktree's badge. Called from `RepoContext.tsx` when that worktree's detail page becomes the focused route (and again on a `window focus` event while still viewing it, covering "alt-tabbed back to an already-open worktree") — "the user is now looking at it" is treated as "seen", independent of whatever actually happens inside the claude session next.
- **Frontend**: `useAttentionStream.ts` owns the `/ws/attention` connection (mounted once, inside `RepoProvider`; reconnects 3s after a close, e.g. a server restart) and returns the current `worktreeId -> message` map, plus an `onUpdate` callback for live (post-snapshot) changes. `RepoContext.tsx` uses that callback to decide whether the person is "in focus" for that worktree — the *route* matches AND `document.hasFocus()` — and if not, calls `playAttentionSound()` (a synthesized two-note tone via Web Audio, no bundled asset) and `maybeDesktopNotify()` (a real OS notification) — both in `attentionNotify.ts`. `Sidebar.tsx` renders a persistent amber pulsing dot (`.sidebar-dot-attention`) next to any worktree present in the pending map, regardless of focus, until the clear call above removes it.
- **Desktop notifications default to on** (`notificationPreference.ts`, a `localStorage` boolean): `RepoContext.tsx` calls `requestNotificationPermission()` proactively once on mount rather than waiting for a settings-modal click, so "on by default" is a real default, not just a UI label — a no-op if permission is already granted/denied, or if a browser (Safari, notably) declines to prompt without a genuine user gesture, in which case the settings modal's Appearance-tab switch doubles as that gesture. `maybeDesktopNotify()` checks both `Notification.permission === "granted"` and this preference before firing, so turning the switch off silences the desktop channel even with permission already granted (the sidebar dot and sound are unaffected either way — this preference and permission only gate the OS-level notification). Clicking a fired notification calls `window.focus()` (only re-focuses *this* tab — a browser-level limit if worktree-studio happens to be open in more than one) and `useNavigate()`s straight to `/repo/:repoId/worktree/:worktreeId` for the worktree that raised it.
- **Spotlight's own indicator moved off the dot look**: it's now a small lamp/spotlight glyph (`icons/StatusIcons.tsx`'s `SpotlightIcon`, `.sidebar-spotlight-icon`) so the plain glowing dot is free to mean exactly one thing — "claude needs you" — without the two competing for the same visual language.
- **Not built (see `PLAN.md`'s TODO, needs a plausibility check first)**: interactive notifications that let you answer Claude's prompt directly from the OS notification (choose an option without switching to the terminal). Blocked on real open questions — the `Notification` API's `actions` buttons require a service worker this app doesn't have, answering would need a new endpoint that types into the right tmux pane, and the Notification hook's `message` is free text with no guaranteed structure to extract real yes/no/options from.

### Global settings modal (`SettingsModal.tsx`)

Opened via a gear icon in the sidebar header, as a big modal rather than a new route (both were viable; the modal fit the existing persistent-sidebar shell more simply). Three tabs, a fixed height (`.settings-modal-body { height: 60vh }`, not `max-height` — it used to visibly resize between tabs of different content length):
- **Installation**: `GET /api/settings/dependencies` (`internal/api/settings.go`) reports tmux/spotlight (detection-only, via `exec.LookPath` + spotlight's known `~/.local/bin` fallback — this tool won't run an installer on the user's behalf) and skill/claude-hook (actionable: real install/uninstall buttons, backed by `internal/skillasset` and `internal/claudehook` respectively — "claude-hook" now covers both the SessionStart and Notification hooks, see "Claude Code Notification hook + attention badges" above). Every dependency's status and every install/uninstall action is independent — one failing never blocks or corrupts another's state or crashes the modal.
- **Appearance**: the dark/light theme switch — a sliding pill toggle (`role="switch"`), not a two-row radio list (an earlier version, replaced per direct feedback that it "didn't look like a beautiful toggle button most websites use") — plus a "Notifications" section for granting desktop-notification permission (see "Claude Code Notification hook + attention badges" above). See `docs/design.md`'s "Light theme" section.
- **Logs**: this server's own recent `ERROR`-level log lines, plus the real log-file path (`~/.worktree-studio/server.log`, mirrored there by `main.go` — previously stdout-only, so a headless/backgrounded run had no durable record). `GET /api/settings/logs` (`internal/api/logs.go`) tails the last 200 lines containing the literal substring `level=ERROR` (a plain substring check matching slog's text-handler output exactly, not a real log parser — same "deliberately basic" call `internal/audit.Logger` makes).
- **The former "Worktrees" tab (a flat, read-only, cross-repo table) was removed** per direct request — it duplicated each repo's own settings page, which already has a Worktrees tab with Local/Imported/Archived sections. `GET /api/worktrees/all` and `store.ListAllWorktreesWithRepo` were removed along with it.
- `internal/skillasset` embeds a copy of this project's own `.claude/skills/worktree-studio/SKILL.md` (`go:embed` can't reach into a dot-prefixed directory to embed the real file directly — Go's toolchain excludes those from package discovery) so "install skill" writes a real copy to `~/.claude/skills/worktree-studio/` regardless of where the running binary's checkout lives. A dedicated test (`skillasset_test.go`) compares the embedded copy against the real file byte-for-byte, so drift between them is a test failure, not silent staleness.

### Per-repo settings page (`RepoSettings.tsx`)

Reached via the gear icon on a repo's own sidebar row (distinct from the global settings modal above). Defaults to its General tab (base-branch override, with a note that it's only as fresh as the last local fetch/pull — prefix with `origin/` for a remote-tracking ref instead). Its Worktrees tab has Local/Imported/Archived sections (the last described above) and a "Created from" column showing each worktree's `source_branch`. A Shells tab lists every open terminal across the repo's worktrees with a deep link to jump to one.

### Storage

- **SQLite** at `~/.worktree-studio/studio.db` via `modernc.org/sqlite` (pure Go, no cgo). Tables: `repos(id, name, path, base_branch)`, `worktrees(id, repo_id, name, branch, path, created_at, status, source, archived_at, source_branch)`, `terminal_sessions(id, worktree_id, tmux_session_name, tab_label, created_at)`, and `worktree_layouts(worktree_id, layout_json, updated_at)` (one saved dockview layout per worktree, upserted wholesale — an opaque JSON blob this server never inspects the shape of). No migration framework — added columns go in via a `PRAGMA table_info` check + conditional `ALTER TABLE`, one small function per column (see `store.go`'s `migrateAdd*` functions).
- **`PRAGMA foreign_keys = ON`** is set once in `store.Open` (real fix, not always-been-true): SQLite does not enforce foreign keys — including every `ON DELETE CASCADE` in the schema above — unless this is set per connection, off by default. Verified empirically (a throwaway script: insert parent+child, delete parent, child row survives) that it was silently unenforced before this fix. Found while adding `worktree_layouts`; `internal/term`'s existing tests had to be fixed too, since they created terminal sessions referencing a worktree id that was never actually inserted — silently worked before, correctly rejected now.
- **Audit log** at `~/.worktree-studio/audit.log.jsonl`, one JSON object per line, written by `internal/audit.Logger.Log(event, fields)`. Every mutating handler in `internal/api` calls it. See `docs/running-locally.md` for how to tail it.
- **Server log** at `~/.worktree-studio/server.log` — `main.go` mirrors its `slog` output there (`io.MultiWriter` alongside stdout) in addition to the console, so a headless/backgrounded run still has a durable error record for the settings modal's Logs tab to read. Deliberately basic, no rotation — same call the audit log already made.
- **`localStorage` (browser, not server-side)**: theme choice (`theme.ts`), file-tree-panel open/closed (`filesPanelPreference.ts`), and the worktree git/PR summary cache (`prGitCache.ts`, 5-minute TTL). None of these are synced to the backend — they're pure client-side preference/cache state, on purpose (see "Sidebar hover popover" above for why the summary cache in particular has to live here, not server-side).
- **File-watcher state** (`internal/files.Manager`'s ref-counted `Watcher`s) is purely in-memory, never persisted — there's nothing to reconcile at startup the way `internal/term.Reconcile` does for tmux sessions, since an fsnotify watch has no meaning across a process restart; a fresh watch is (re-)created lazily the next time a `/ws/files/:worktreeId` client subscribes.
- **Spotlight state** is NOT in worktree-studio's own store at all — the external `spotlight` CLI owns its own state file (which repo root is mirrored from which worktree, tracked by that tool, not queried here directly; `internal/spotlight.List`/`StatusForRoot` parse its `spotlight list` output instead). worktree-studio treats it as an external system to query, not data it's responsible for persisting.

### Frontend embedding

`cmd/worktree-studio/main.go` imports `worktree-studio/web`, a tiny package whose only job is holding `//go:embed all:dist` — go:embed patterns resolve relative to the *file* containing the directive, so the embed can't live in `cmd/worktree-studio` (a different directory from `web/dist`). `web/dist/.gitkeep` is checked into git so the directory (and thus the embed) always exists on a fresh checkout, even before `bun run build` has ever run — `go build ./...` works either way. At runtime, `mountFrontend` checks for a real `index.html` in the embedded FS; if it's missing (only the placeholder is there), it serves a small "run `bun run build`" HTML page instead of a blank/broken UI. Once a real build exists, static assets are served with an SPA fallback to `index.html` for client-side routes like `/repo/:id`.

### What's explicitly NOT built yet

Per `PLAN.md`'s build order, none of the following exist yet — don't assume they do:
- Git diff view + comment-to-agent (step 6 / TODO) — the file editor from step 5 exists (see "In-browser editor" above), this is its own follow-up step
- An engine-picker UI for the editor — the `web/src/editors/registry.ts` adapter registry supports more than one editing engine, but only CodeMirror is registered and there's no UI to choose between engines
- OS-level popout for terminals is not a TODO at all — it was considered and ruled out.
- Terminal websocket connections are NOT multiplexed over one shared channel — each terminal has its own dedicated `/ws/terminals/:id` connection (a deliberate simplification vs. PLAN.md's originally-sketched single-multiplexed-channel design; see `docs/session-persistence.md`).
- Spotlight is a thin wrapper — it does NOT reimplement any sync logic, has no manifest/staging/lock scheme of its own (that was an earlier, wrong design; see `docs/spotlight-sync.md`'s "design correction" note), and there's no per-workspace/per-subdirectory scoping — it always mirrors an entire worktree into an entire root.
- Git/spotlight status is REST-polled (every 15s, for recently-viewed worktrees only — see `RepoContext.tsx`'s `StatusScheduler` above), not pushed over a websocket. There's no server-side push/broadcast mechanism anywhere in this codebase — a deliberate, recorded choice, not an oversight, and revisited (audited for leaks, not replaced) after a direct question about it.
- There's no one-click "Resume claude session" action — the audit log records what's needed for it, but a person still runs `claude --resume <id>` themselves. No bulk-select/bulk-delete UI for worktrees either — the 60-day archived-worktree retention sweep (see "Worktree lifecycle status" above) covers the original motivating use case for that without needing one.

See `docs/running-locally.md` for how to run this step's server + frontend, and `.claude/skills/worktree-studio/SKILL.md` for the agent-facing usage doc.

## 2026-09-01 — Fixed the 55 broken "can't find session" terminal tabs, and built a real orphan-cleanup command so it's never hand-rolled again

Direct fallout from the previous entry's cleanup: it killed tmux sessions directly while the server (up 39 minutes) kept running. `Reconcile` only runs at server startup, so the DB never noticed — **57 `terminal_sessions` rows, only 2 backed by a live tmux session.** The other 55 showed as normal-looking tabs that, on attach, rendered tmux's own `can't find session: ...` stderr as if it were pane output (`handleTerminalWS`/`term.Attach` treat a fast-exiting `tmux attach-session` as a successful attach — nothing detects or flags this case). User asked to hold off on any bulk delete/restart pending a real answer to "can we tell if a session was actually used recently?" before anything gets pruned again.

**Confirmed tmux exposes exactly that**: `#{session_activity}` (last output in any pane — not just keystrokes, so a `claude` session producing output on its own counts) and `#{session_last_attached}`. Verified against the 2 real live sessions before relying on it. Important asymmetry surfaced along the way: this only helps for sessions tmux still knows about. The 55 already-dead rows have no activity data left to check — the shell is already gone regardless of recency, so pruning those DB rows loses nothing. User agreed to prune just those 55 (via the app's own `DELETE .../terminals/{id}` endpoint, scripted across all 55 — normal `CloseSession` path, audit-logged, no server restart, the 2 live sessions untouched).

**Built the actual safeguard** rather than leaving this as a one-off shell exercise, since "kill whatever looks orphaned" is exactly what caused the previous incident:
- `internal/term/orphans.go` — `FindOrphanTmuxSessions`/`KillOrphanTmuxSessions`. "Orphan" here is the *opposite* mismatch from `Reconcile`: a live `wts-`-prefixed tmux session with **no** `terminal_sessions` row (a leaked test session, one made by hand), not a dead session with a lingering row. Each orphan is flagged `Protected` if `session_activity` falls within a caller-given `minAge` window; `KillOrphanTmuxSessions` kills only the unprotected ones and **has no override** — no `--force`, nothing. A caller wanting a shorter window passes a smaller `minAge` explicitly at the call site; the check itself can't be silently bypassed. A session whose activity can't be read is treated as protected, not assumed safe.
- `internal/api/orphans.go` — `GET /api/orphan-tmux-sessions` (list/preview, read-only) and `POST /api/orphan-tmux-sessions/prune` (kills, audit-logs each kill as the new `orphan_tmux.kill` event — added to `internal/audit/events.go`, `web/src/auditEvents.ts`, and `WorktreeAuditLog.tsx`'s `EVENT_LABELS`, though it'll never actually render in the per-worktree audit view since an orphan by definition has no `worktree_id`). Default safety window is 7 days, overridable via `?min_age_hours=`.
- `cmd/worktree-studio/orphans.go` — `worktree-studio orphans [--kill] [--min-age=<duration>]`, wired into `main()` the same way as `open-file`/`spotlight` (talks to the running server over HTTP, doesn't reimplement anything locally). Lists by default; `--kill` prunes and prints what was killed vs. protected.
- Documented in the skill file's "Using terminals" section (right next to the existing "poke at tmux directly" debugging tip, since that's exactly where someone would otherwise reach for a hand-run `tmux kill-session`) and in the README's CLI subcommand list.

**Verified**: new `internal/term` tests cover the actual safety property directly — a freshly-created orphan survives a sweep with a 1-hour window (`Protected`, still alive in tmux afterward) and the same orphan gets killed with `minAge=0` (deterministic without any wall-clock sleep, since `session_activity` is always ≤ the moment `FindOrphanTmuxSessions` computes its cutoff); also that a DB-backed session is never reported as an orphan regardless of activity, and that a plain non-`wts-`-prefixed session (something a user made themselves) is never touched. New `internal/api` tests cover the same two cases end-to-end over HTTP, plus that a real, DB-backed terminal session survives a `min_age_hours=0` sweep targeting a co-existing genuine orphan. `go build`/`go vet`/`gofmt` clean, `go test ./...` fully green — including `skillasset.TestEmbeddedCopyMatchesRealSkillFile`, previously failing and flagged as pre-existing/deferred in the prior entry, fixed as a mechanical side effect of syncing `internal/skillasset/SKILL.md` after editing the real one.

**Follow-up, same session: closed the "still looks broken" gap flagged above.** `handleTerminalWS` now calls the new `term.HasSession` before attaching; if the session's already gone it writes one clear line ("this terminal's session no longer exists ... close this tab") over the websocket instead of calling `term.Attach` at all — before this, `tmux attach-session` "succeeded" (the pty process starts fine) while tmux itself exited immediately and wrote its own `can't find session: ...` to stderr, which got relayed through the pty byte-for-byte as if it were real pane output. Deliberately does **not** delete the row itself from this handler — that stays the job of `handleDeleteTerminal` (closing the tab) or the next `Reconcile`, so there's still exactly one path that removes a `terminal_sessions` row, not two competing ones. While in the same function, fixed the sibling case right next to it: a genuine `term.Attach` failure (a real, rare `pty.Start` error, not a missing session) was sending a JSON blob (`{"type":"error",...}`) that the frontend has never actually parsed — `Terminal.tsx`'s `ws.onmessage` just writes any string straight into the pane — so that path was rendering raw JSON as garbled terminal text on the rare occasion it fired. Now a plain-text line, consistent with the new dead-session message and with what the frontend actually does with it.

New end-to-end test (`TestTerminalWSRefusesAttachToDeadSession`): creates a real terminal, kills its tmux session directly (the same state 55 real rows were just found in), dials the websocket, and asserts the first message is the friendly line — not `can't find session` — that the row survives untouched, and that closing the tab afterward still returns 200. ## 2026-08-31 (latest) — Root-caused and fixed the "orphaned tmux session" leak: it was the test suite, not production

User asked to stop tmux sessions leaking, hypothesising it was caused by leaving terminals open or archiving worktrees. **Both hypotheses were wrong, and so was this log's earlier framing of it** (an earlier session speculated the orphans had "accumulated over months from sessions killed outside the app" — never verified, and incorrect).

**Production code was already correct on every path**, verified by reading rather than assuming:
- Archiving only runs `UPDATE worktrees SET status/archived_at` — no row deletion, so the `terminal_sessions.worktree_id ... ON DELETE CASCADE` never fires.
- Deleting goes through `api.hardRemoveWorktree`, which closes terminal sessions *before* deleting the worktree row (its comment already notes this exact orphan hazard was caught during step 7.4).
- The 60-day archive sweep reuses that same safe teardown.
- There is no `DELETE FROM repos` anywhere, so the repo→worktree cascade can't fire either.

**Actual root cause: `internal/term`'s tests ran against the developer's REAL tmux server.** Every test session is an orphan by construction (the test store is a throwaway temp-dir SQLite file, so `Reconcile` can never see those sessions). Confirmed empirically: all 61 orphans were rooted in `/var/folders/.../T` temp dirs — **zero real user sessions**. A clean passing run leaks 0 (measured); leaks only survive an abnormal exit (`go test` timeout, Ctrl+C, panic) that skips `t.Cleanup`.

**A worse, previously-unnoticed consequence of the same design**: `CreateSession` sets server-wide options (`mouse`, `set-clipboard`, `set-titles`, `xterm-keys`, `extended-keys`) and rebinds the global copy-mode key tables. Since the tests call it, **running `go test` silently reconfigured the developer's live tmux server and every session they had open.**

- **Fix** (`internal/term/tmuxcmd.go`, `internal/term/main_test.go`, `internal/api/main_test.go`): added `term.TmuxCmd(...)`, which targets a dedicated tmux server (`tmux -L worktree-studio-tests`) under `go test` and the real server otherwise; converted all 25 hardcoded `exec.Command("tmux", ...)` call sites in `internal/term` plus 7 more in `internal/api`'s tests to route through it. Production behavior is unchanged — worktree-studio still deliberately uses the ordinary tmux server so sessions survive a restart and stay reachable from a plain `tmux attach`. `TestMain` (in both packages) calls `KillTestTmuxServer` at **both** ends; the startup kill makes a crashed prior run self-healing rather than merely less likely.
- **The first version of this fix was wrong, and the way it failed is the interesting part.** It gated isolation on a package-level variable set by `internal/term`'s own `TestMain` — which silently missed `internal/api`'s terminal tests, since **a `TestMain` is per test *binary***: those tests build a `term.Manager` and call `CreateSession` from a different binary where term's `TestMain` never runs. Nine fresh orphans appeared within minutes of declaring the leak fixed. Reworked so isolation is decided **automatically** inside `term.TmuxCmd` (test binaries are detected by the `.test` suffix on `os.Args[0]`, avoiding an import of `testing` from non-test code; `WORKTREE_STUDIO_TMUX_SOCKET` overrides). Opt-in isolation is the wrong shape for this — any future package calling into `internal/term` would have regressed it just as silently.
- A second, related gap in the same batch: `internal/api`'s tests also called `tmux` *directly* to assert on sessions, so once `term` moved to the isolated server those assertions were querying the wrong one (4 tests failed). They now go through `term.TmuxCmd` too, which is why it's exported.
- **Cleanup**: killed the 61 original orphans, then the 9 the incomplete fix produced — each verified unattached *and* temp-dir rooted before killing. State is now exactly in sync: **52 live tmux sessions, 52 DB rows, 0 orphans, 0 stale rows.**

**Verified — and note that two verification attempts along the way were themselves broken.** (1) A safety check written with `awk` silently emitted empty fields (`awk` isn't available in this shell), flagging every session as unsafe; it failed *safe* and nothing was killed, but the lesson is to verify the checker before trusting a kill list. Redone in `python3`. (2) A delta-0 session count was briefly treated as evidence of isolation — it isn't: a clean run was delta-0 *before* the fix too, since passing tests clean up after themselves. That number can't distinguish "never touched the real server" from "touched it and tidied up."

What actually proved it, run while the suite was executing: **polling both servers concurrently during a full `go test ./...`** showed sessions appearing on the isolated server while the real server stayed pinned at exactly 52 and never reached 53. Plus: a stray session planted on the test socket was cleaned by the next run's startup kill (self-healing confirmed), and the real server's session count, DB sync, and global options were unchanged across runs. `go build`/`go vet`/`gofmt` clean.

**A third mistake, this one introduced by the fix itself and caught by its own verification:** giving both test binaries the *same* socket name meant each package's `TestMain` killed the shared server out from under the other, since `go test ./...` runs packages in parallel. It surfaced as `term.TestCurrentPathAfterCd` failing **only** when `term` and `api` ran together, and passing 3/3 alone. Fixed by deriving the socket per test binary (`worktree-studio-tests-term`, `-api`, ...) from `os.Args[0]`, and by making `KillTestTmuxServer` only ever kill the current binary's own server.

**`term.TestCurrentPathAfterCd` flakiness — root-caused and fixed (pre-existing, but adjacent enough to fix here):** the per-binary socket fix took it from failing consistently in that combination to 2/3, proving the cross-kill was real but not the whole story. The rest was a genuine timing race: its `sendKeys` helper waited a fixed `time.Sleep(1s)` for `cd` to take effect, which held when `internal/term` ran alone but not when parallel `internal/api` tmux tests loaded the machine. Replaced with `waitForPanePath`, a bounded poll (10s cap, 50ms interval) — more reliable *and* faster, since it waits exactly as long as needed. Now 4/4 clean on the exact previously-failing combination and 2/2 on full `./...`. A prior session had diagnosed this and named this same fix direction without applying it.

**Still flaky / failing, NOT fixed (both pre-existing, neither related to this change):** `spotlight.TestStartSwitchingWorktreeStopsPrevious` flaked once under full-suite load, then passed on every subsequent run (no dependency on `internal/term`). `skillasset.TestEmbeddedCopyMatchesRealSkillFile` still fails and was re-confirmed via `git stash` to predate all of this — it needs `internal/skillasset/SKILL.md` re-synced from `.claude/skills/worktree-studio/SKILL.md`. Both are small, separable fixes, deliberately not bundled in here.

**Still open, deliberately not built:** a settings-modal "warnings" tab showing this count was requested, but the premise changed once the orphans turned out to be test-only — a production orphan counter would read 0 for real users. Worth deciding what it should actually measure (stale-row count is a real, non-zero signal; orphan count is not) before building it.

## 2026-08-28 — Fixed: clipboard addon silently dropped tmux's OSC 52 relay (Problem 8)

Doing the live-browser re-confirmation that Problem 7's fix (below) still owed — using real OS-level mouse drags via browser automation, not JS-dispatched synthetic events (those turned out to be silently ignored by xterm.js entirely) — found a second, previously-undetected bug stacked on top of Problem 7's: a real drag correctly landed the dragged text in tmux's own buffer (`tmux show-buffer`), and a raw-websocket-frame capture confirmed a well-formed `\x1b]52;;<base64>\x07` frame really did reach the browser — but a `navigator.clipboard.writeText` monkeypatch on the live page never fired.

- Root cause, found by reading `@xterm/addon-clipboard@0.2.0`'s actual shipped source (not its docs/types): its default `BrowserClipboardProvider.writeText` only calls `navigator.clipboard.writeText` when the OSC 52 selection field is exactly `"c"` — anything else, including the empty field (`;;`) tmux has always sent (confirmed via the raw frame capture, and consistent with every OSC 52 capture in this whole document going back to Problem 2), is a silent no-op with no error anywhere.
- This means the browser-side half of clipboard relay had likely never actually worked in this app before now — every earlier "verified" claim in `docs/terminal-clipboard.md` stopped at "the OSC 52 byte sequence reached the pty/websocket," which turns out to have been necessary but not sufficient.
- **Fix** (`web/src/Terminal.tsx`): a custom `IClipboardProvider` (`alwaysSystemClipboardProvider`) that ignores the selection field and always relays to `navigator.clipboard` — there's only one real clipboard a browser exposes anyway. Passed into `ClipboardAddon`'s constructor in place of its default provider.

## 2026-08-21 (later) — Re-fixed wheel-scroll by restoring `mouse on`; root-caused why it's actually required

Continuation of the same day's earlier revert (see the entry below this one): after reverting `allow-passthrough`, the user still reported the identical symptom in a plain shell — "still cycles through in shell" — even after a hard reload and a brand-new terminal tab, so the `allow-passthrough` revert alone hadn't fixed it. Root-caused properly this time, with live evidence rather than reasoning alone:

- Added temporary diagnostic logging to `internal/api/terminals.go`'s websocket read loop (since removed) to capture the raw bytes a scroll actually sends to the pty. It showed literal `\x1bOA`/`\x1bOB` (application-cursor-keys arrow bytes) on every wheel tick, in a plain shell with tmux's own state confirmed completely ordinary (`mouse_any_flag=0`, `alternate_on=0`, `pane_in_mode=0`).
- Traced this to `@xterm/xterm`'s own wheel handler (`src/browser/CoreBrowserTerminal.ts`): it converts wheel scroll into literal cursor-key bytes whenever `!this.buffer.hasScrollback` **and** no active mouse-tracking protocol already claims wheel events. A live capture of a genuine `tmux attach-session` client attach (throwaway Python pty script) showed tmux sends `\x1b[?1049h` (enter alternate screen) to *every newly-attaching client*, unconditionally, as its own full-repaint-on-attach mechanism — regardless of the pane's real buffer state. That makes `buffer.hasScrollback` permanently false for *any* tmux-attached xterm.js session, plain shell or not, which is exactly the "no scrollback" condition the wheel handler treats as "must be a fullscreen app — send arrow keys instead of scrolling."
- The only thing that stops that fallback from firing is tmux's own mouse-tracking protocol being active (`mouse on`), which makes xterm.js send wheel events as SGR mouse reports instead — exactly what tmux's own default root-table binding needs to route wheel-up into copy-mode and scroll tmux's real scrollback. So the morning's `mouse off` revert (Problem 4) and this bug are the same tradeoff, not two independent regressions: `mouse on` is required for wheel-scroll to work at all in any tmux-attached session; it's also what suppresses xterm.js's *unforced* native selection.
- **Fix**: restored `mouse on` in `internal/term.CreateSession`. Native selection/copy still works via xterm.js's own Shift/Option force-selection convention (already documented as "the actual, proper fix" for Problem 4) — that conclusion didn't change, it just needed `mouse on` back underneath it. Renamed `term.DisableGlobalMouseAndPassthroughCapture` → `term.CorrectGlobalMouseAndPassthroughSettings`, which now corrects `mouse` back to `on` (and keeps `allow-passthrough` reverted to `off`) at every startup, for an installation that already ran the briefly-`mouse off` version. `docs/terminal-clipboard.md` gained a "Problem 6" section with the full mechanism and citations; Problem 4's conclusion updated to point at it. Removed the temporary diagnostic logging (and its now-unused `fmt` import) from `terminals.go` now that the bug is root-caused and fixed.
- Considered and rejected: overriding xterm.js's wheel handling client-side via its public `attachCustomWheelEventHandler` API to bypass this independent of the `mouse` option. Rejected because tmux, not xterm.js, owns the real scrollback for an attached session — a client-side-only override could suppress the wrong behavior but couldn't make scrolling actually work without tmux also treating the event as a mouse report, which still needs `mouse on` underneath it anyway.

**Verified:** `go build ./... && go vet ./... && go test ./...` — 167 tests passing. Not yet re-confirmed live by the user (scroll fix + Problem 4's Shift-force-selection convention for copy) — that's the next thing to check.

## 2026-08-11 — Bug fixes: worktree base branch, terminal tab labels, split-pane padding

Four issues reported after using the toolbar/settings-page rework from the previous session (`b8f72a2`/`eece2fb`/`3421289`/`6e8b475`):

- **New worktrees didn't reliably branch off "the" base branch.** `gitops.AddWorktree` ran `git worktree add -b <branch> <path>` with no explicit start point, so git's own default applied: whatever the main repo checkout's HEAD happened to be at that moment — not necessarily any particular base branch, and silently wrong if the main checkout was itself left on a feature branch. Since there's no fully reliable way to always know "the" base branch (a repo might have no `origin`, or use an unconventional default-branch name), added both an auto-detect **and** a per-repo override, per direct request ("if it is not trivial to find the base branch, let's have a setting"): `gitops.DetectDefaultBranch` tries `origin/HEAD`, then local `main`, then local `master`, then gives up (empty, meaning fall back to git's old implicit-HEAD behavior); `Repo.BaseBranch` (new `repos.base_branch` column, migrated in) is an explicit override, settable from the repo settings page's new **General** tab or `PUT /api/repos/:repoId/settings`. `handleCreateWorktree` prefers the override, falls back to auto-detect, and logs the resolved `base_branch` on the `worktree.create` audit event.
- **Terminal tabs sometimes showed a blank or stale label instead of "shell"/"claude".** Two separate bugs: (1) the frontend rendered `ts.tab_label` directly in a few places without the same `|| "shell"` fallback the backend already applies on create, so any session with an empty `tab_label` (e.g. from before that backend default existed) rendered a blank tab forever; (2) tmux only emits a pane's OSC title escape sequence to a client on an actual title *change*, not on a fresh attach — so reloading the page (or navigating back) while `claude` was already running in a pane showed the generic label/icon until something inside the pane happened to touch its title again. Fixed (2) with `internal/term.CurrentTitle` (`tmux display-message -p '#{pane_title}'`) + `handleTerminalWS` replaying it as a synthetic OSC sequence right after attaching, so the frontend's existing title-change-driven detection (`terminalAppDetection.ts`) gets the right answer immediately on connect instead of waiting for the next real change.
- **Split-right/split-down panes had no left/top padding**, text flush against the pane edge (screenshot-reported). ## 2026-08-07 — Bug report: Ctrl+C/Ctrl+V don't work in browser terminals

User reported the most basic terminal actions — copy (Ctrl+C) and paste (Ctrl+V) — silently doing nothing in the xterm.js terminal panels.

**Root cause**: xterm.js's own key handling calls `preventDefault()` on virtually every keystroke it translates into pty bytes, including Ctrl+C (which must reach the shell as a real `0x03`/SIGINT byte for a real terminal to work at all) — that same `preventDefault()` also suppresses the browser's native copy action, so "select text, press Ctrl+C" never had anywhere to go. This is a well-known xterm.js integration gap (not a regression from anything built this project) — the embedding app is expected to wire this up itself via `attachCustomKeyEventHandler`, which nothing in `Terminal.tsx` did.

**Fixed**: `Terminal.tsx` now intercepts Ctrl+C/Cmd+C — if there's an active selection, copies it via `navigator.clipboard.writeText` and suppresses the keystroke (so it doesn't also send a literal SIGINT); with no selection, lets it through as a normal interrupt, so `Ctrl+C` at a running prompt still works exactly as before. Ctrl+V/Cmd+V is handled explicitly via `navigator.clipboard.readText()` → `term.paste(text)`, rather than relying on xterm's own native-`paste`-event wiring (which does exist in xterm.js's source, but explicit handling removes any ambiguity about whether it was actually the failure point). Both Ctrl- and Cmd- modifiers are handled, since this runs on macOS but Ctrl+C/Ctrl+V is common muscle memory regardless of OS.

The key-combo decision logic (`classifyTerminalKeyEvent`) is a small pure function, extracted specifically so it's unit-testable without a real browser or a real xterm `Terminal` instance — the actual clipboard/xterm glue isn't independently testable in this environment (no browser automation tool connected this session; same honest limitation `Terminal.tsx` has always had, per every earlier PROGRESS entry that touched it).

**A second real bug found immediately after, while explaining the design to the user (not by the test suite — this is exactly the kind of thing pure-logic unit tests can't catch)**: the paste branch returned `false` from `attachCustomKeyEventHandler` but never called `event.preventDefault()`. Returning `false` only tells xterm.js to skip *its own* keydown→bytes translation — it does not suppress the browser's native default action for that keystroke. Since xterm.js already has its own listener for the browser's native `paste` ClipboardEvent (separate code path, not gated by `attachCustomKeyEventHandler` at all), leaving the keydown's default action un-prevented meant that native listener could *also* fire, on top of the explicit `clipboard.readText()` → `term.paste()` call — pasting the clipboard content twice. Fixed by adding `event.preventDefault()` to the paste branch specifically (the copy branch doesn't need it: worst case there, a redundant native copy of the exact same selection text is harmless).

**Verified:**
- `bun run build`/`bun run test` clean — **35/35** (8 new in `Terminal.test.tsx`, covering Ctrl+C/Cmd+C/Ctrl+V/Cmd+V classification, case-insensitivity, Ctrl+Shift+C passthrough, unrelated Ctrl-combos, plain unmodified keys, and keyup events all correctly falling through to "pass").
- Confirmed `attachCustomKeyEventHandler` present in the real built production JS bundle (`web/dist/assets/index-*.js`), not just the source.
- **Not verified**: actual copy/paste behavior in a real browser — no browser automation tool is connected this session. The fix is the standard, well-documented pattern for this exact xterm.js gap (the same approach used by VS Code's integrated terminal, Hyper, and other xterm.js-based apps), and the bundle contains the code, but a real click-through is still worth doing to confirm it feels right, same caveat as every prior UI change in this project made without a browser tool available.

## UI redesign: design system, three themes, rows-not-cards (2026-08-25)

Direct ask: "Need a UI revamp. 2–3 themes, one modern, one classic, with simple no-cards-like UI that is easy on the eyes for regular work… should be a long term usable app, part of dev flow… not with resentment, but delight and not be overwhelmed."

Started from a diagnosis of the shipped UI rather than a taste argument — nine measurable properties, each costing attention on every glance. The full write-up (diagnosis, principles, live switchable theme mock) is an artifact: https://claude.ai/code/artifact/29f2d70e-6b5e-43fa-9e03-d205bbfb8ebf. The durable version lives in `docs/design-system.md`; `docs/design.md` is now a pointer to it.

**What was actually wrong** (from real screenshots at ~20 worktrees): every row was a bordered card, so a list of 20 branches read as 20 separate objects; four accents were in play with `--green` meaning "selected" *and* "clean" *and* "active"; the worktrees table printed the same 62-character path prefix on every row (wrapping over three lines) while head-truncating the branch name — the only part that differed; the most prominent string in the workspace was `[No pull request for this branch]`; the Appearance tab put two controls in a ~1000×900 box; there was no filter, collapse or ordering for 20+ rows; and `--text-dim` measured **4.19:1**, below the 4.5:1 floor, while carrying every label and timestamp in the app.

**Six commits, each shippable alone:**

1. **`tokens.css` becomes a contract, not a theme.** Every palette block defines exactly the same token names — a theme needing a new token is a redesign, and that guardrail is what stops the file sprawling back into per-component colour soup. Added `--text-3`, `--attention`, `--accent-on`, `--row-h`, `--radius`, fixed type/space/motion scales. Three families (Graphite/Ledger/Deck) on a `data-theme` × `data-mode` axis. Old token names survive as aliases pointing at the contract, so unconverted stylesheets kept working and kept re-theming.
   - `data-mode` is **always** a resolved `dark`/`light`; `system` is storable but resolved in `theme.ts` and the pre-paint snippet, never in CSS. Keeps the stylesheet a flat set of palette blocks with no `prefers-color-scheme` branch, and keeps "follow the OS" an explicit choice — the original argument for having no media query at all. `main.tsx` subscribes via `watchSystemMode` so it stays live.
   - Palette blocks are element-scopable (`[data-theme][data-mode]`, not `:root[data-theme=…]`) so the Appearance tab's theme swatches are **real palettes on a nested element** rather than hand-copied hexes — a preview can't drift from what it previews. Bare `:root` still carries a complete Graphite-dark palette, so the app renders correctly if the attributes are never stamped.
   - Command Deck's `--text-dim` lifted #6b7684 → #7c8694 (4.19:1 → 5.25:1); the original demoted to `--text-3` where it only carries counts.
2. **Sidebar: rows, not cards.** No border/radius/background on a worktree row; separation is row height, indentation and space between groups. Selection is a wash plus a 2px accent rail on exactly one row. Chevrons and per-repo actions hidden until hover **or focus-within** (a pure `:hover` reveal silently breaks keyboard access). Glow removed from the attention dot — it stays findable by being the only saturated fill left. Branch names middle-truncate via `branchLabel.ts`: the head shrinks and ellipsises while the tail is pinned at natural width, so the browser still does the measuring and it stays correct at any width.
3. **Chrome pass** across base/dialogs/badges/dependency/palette/worktree-detail/file-tree/editor. The terminal loses its frame (it was a bordered rounded inset box, inside a bordered panel, inside a padded container). Branch name moves ahead of the PR link, and an absent PR renders nothing. One selection language everywhere, replacing four different treatments. **Two judgement calls worth recording, both deliberate departures:**

- **Rows are NOT sorted attention-first**, despite that being the obvious reading of "the sidebar answers *what needs me?*". Attention arrives asynchronously over `/ws/attention`, so rows would reorder themselves underneath the pointer at exactly the moment you were reaching for one. Attention is surfaced by counting, marking and filtering instead. Noted in `Sidebar.tsx` so the omission doesn't read as an oversight.
- **`Cmd+B` doesn't accept `Ctrl` inside a terminal.** `Ctrl+B` is tmux's default prefix and every terminal here is a tmux session, so the usual `metaKey || ctrlKey` would have stolen it. `keyboard.ts`'s `hasSafeModifier` honours `Ctrl` only outside a text-entry target — which keeps the shortcut working on Linux/Windows without breaking the prefix. The same guard stops `/` swallowing most of the slashes typed into a shell.
